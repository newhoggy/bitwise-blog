Bug for bug: what jq compatibility means

Why succinctly jq reproduces jq 1.7.1's quirks, when it is allowed to differ, and how every difference is checked and written down.

  • succinctly jq gives the answer jq 1.7.1 gives, quirks included. It departs only on a short, closed list of grounds, every departure is written down, and the comparison run fails on any difference it finds that is not.
  • A drop-in replacement is only drop-in if the scripts you already have keep printing what they printed. Writing every difference down means you can read what will change before you switch, instead of finding out in production.
  • The common mistake is to hear "compatible" as "correct by some standard", or as "the same as the newest jq". It means the observable behaviour of one pinned binary, its accidents included.

This page is one of three that go with the succinctly 0.8 announcement. Every output on it was captured from three binaries on macOS (arm64): the system's jq 1.7.1, Homebrew's jq 1.8.2 and the released succinctly 0.8.0, whose sjq alias is succinctly jq.

What should a jq replacement print?

Start with a file that is not quite JSON: an array with a stray NUL byte glued to a number. What should a jq replacement print for it?

printf '[1\0x,2]\n' | jq -c .
All three print the same array, and the x is gone.
Resultjq 1.7.1jq 1.8.2succinctly jq 0.8.0
stdout[1,2][1,2][1,2]
exit status000

Note the newline at the end; the next section shows why it matters. A careful parser would reject this text: 1, a NUL and an x are not a number. jq reads it as [1,2] because it hands each number token to its number parser as a C string, and a C string ends at the first NUL, so the x is never seen. That is an accident of jq's implementation, and the jq manual says nothing about it. But it is what jq does, so a pipeline that has been feeding jq such files has been getting [1,2], and a "fixed" replacement would break that pipeline the day it was installed.

Ducky asks

Why would anyone want a copy of jq's bugs?

Nobody wants the bug for its own sake. What they want is that swapping jq for sjq changes nothing they did not ask for. A replacement that tidies up jq's surprises makes changes nobody requested, and the people it hurts are exactly the ones who depended on what jq really printed. So the specification is not the manual or the JSON standard. It is the observable output of one binary, jq 1.7.1, pinned by version. That is what bug for bug means here, and succinctly's ADR-0018 makes it the rule.The rule also says how a fact about jq is admitted: only when it was captured from the pinned binary with the command shown, never recalled and never inferred from succinctly's own output.

succinctly is written in Rust, which has no C strings, so this answer did not come for free: reading the NUL as jq reads it took its own fix (#7437).

A first rule: match jq 1.7.1 everywhere

The simplest version of the rule is "whatever 1.7.1 prints, print that". It is about right, and it breaks on the same byte one step later.

Move the NUL to sit between two whole values, and leave off the final newline:

printf '[1]\0[2]' | jq -c .
jq 1.7.1 prints the first value, drops the second and reports success.
Resultjq 1.7.1jq 1.8.2succinctly jq 0.8.0
stdout[1][1][1]
stderr(nothing)jq: parse error: Invalid numeric literal at line 1, column 5jq: parse error: Invalid numeric literal at line 1, column 5
exit status055

The cause is the same C-string habit, one layer up. jq 1.7.1 reads its input in pieces of up to 4,095 bytes, and when a piece holds no newline it measures it with strlen, which stops at the NUL. Everything after the NUL in that piece is thrown away without a word. In a short file with no trailing newline, the whole file is one such piece, so [2] is never read, and the exit status says all went well.

Matching that would mean a replacement that silently loses records and reports success. That is the crack in the first rule: some of jq's behaviour is not a quirk that someone's script relies on, it is damage to their data.

Ducky asks

Hang on. The first example dropped the x too. Why is that one fine and this one not?

Look at what goes missing. In the first example, every value in the text comes out: the bytes jq skips are the inside of one malformed token, and the array still has both its numbers. In this one, a complete, valid value disappears, and the exit status hides it. The first is a reading of bad input that you might depend on; the second loses good input.

So the rule needs exceptions, but a list that grows whenever someone finds jq's behaviour odd is no rule at all. ADR-0018's answer is a closed list. succinctly may depart from the pinned jq only when:

  1. jq emits output it cannot itself read back;
  2. matching would corrupt a document or silently discard data;
  3. matching would take the process down (succinctly is a library as well as a command, so its crash is its caller's crash); or
  4. no portable dependency can express jq's behaviour, which has to be shown with a written table of the candidates that were considered.

"The reference's behaviour is surprising", "our architecture makes it awkward" (without that table) and "the other mode does it differently" are named in the ADR as reasons that do not qualify. And every departure must be recorded on the jq limitations page: in the ADR's words, a divergence that is not written down is a bug that has not been found yet. The dropped [2] falls under the second, since matching would mean losing input while reporting success, and the limitations page records it (#5654).

Notice the middle column of the table: jq 1.8.2 agrees with succinctly here. Upstream fixed the truncation as a security bug (CVE-2026-33948). That is a second reference point, and it raises the next question.

Go deeper: where the NUL rows still differ from both jq releases

Not every NUL row is settled. With the NUL inside an array and no newline, the three tools give three answers, captured with printf '[1\0,2]' | jq -c .:

Resultjq 1.7.1jq 1.8.2succinctly jq 0.8.0
stdout(nothing)[1,2](nothing)
stderrjq: parse error: Unfinished JSON term at EOF at line 1, column 2(nothing)jq: error (at <stdin>:0): Invalid JSON text: expected ',' or ']', found '\0'
exit status505

The limitations page says so in as many words: jq 1.8.2 reads this as [1,2], and succinctly jq does not follow that change yet. A recorded residual is still a difference, but it is one you can look up rather than trip over.

Which jq? Follow 1.8.2 where it fixed a bug

jq 1.8.2 exists, and it disagrees with 1.7.1 in dozens of places. A replacement pinned to 1.7.1 has to decide what to do about each one.

The tempting answer is "follow the newest jq". But 1.8 did not only fix bugs; it also changed the language and added limits, and following those would change answers that 1.7.1 users get today and that were not wrong. So the rule succinctly applies is narrower: where upstream fixed a 1.7.1 answer as a bug, give 1.8.2's answer; otherwise stay with 1.7.1. Each such case is still recorded, as a difference from the pin with the category newer-than-primary.

Here is one a jq user is likely to meet. last(f) of an f that produces nothing:

jq -nc '[last(empty)]'
jq 1.7.1 invents a null; jq 1.8.2 and succinctly produce nothing.
Resultjq 1.7.1jq 1.8.2succinctly jq 0.8.0
stdout[null][][]
exit status000

jq 1.7.1 defines last(g) as reduce g as $item (null; $item), and a reduce always produces one value, so when g is empty you get the seed, null. That made last disagree with first, which yields nothing. jq 1.8 changed it in a commit titled "fix: make last(empty) yield no output values" (jqlang/jq#3179), listed in its release notes under changes to existing functions. That is upstream calling the 1.7.1 answer a bug, so succinctly follows 1.8.2 (#7518).

Ducky asks

If 1.8.2 is right about this, why not just target 1.8.2 and be done?

Because 1.8.2 is a different language in places, and plenty of jq installed today is not 1.8: the jq bundled with macOS, for one, is 1.7.1. Targeting 1.8.2 would change the meaning of programs written against the jq people actually run. The narrow rule takes 1.8's corrections and leaves its redesigns alone.

A fix, a feature or a guard

The narrow rule turns on one question: did upstream call the change a bug fix? Try it on a change that is not.

jq 1.8 added Tcl-style comment continuation: a comment that ends in a backslash (an odd number of them) carries on to the next line (jqlang/jq#2989). Its release notes list it under language changes, not under fixes. Here is a three-line program where it matters:

1
# a comment ending in a backslash \
+ 2
jq -n -f prog.jq
In 1.8.2 the comment swallows the + 2.
Resultjq 1.7.1jq 1.8.2
stdout31
Predict: what does succinctly jq -n -f prog.jq print, 3 or 1? Decide before you open this.
Resultjq 1.7.1jq 1.8.2succinctly jq 0.8.0
stdout313
exit status000

3, as jq 1.7.1 prints. Upstream presents the continuation as a new language feature, not as a repair of something 1.7.1 got wrong, so the pin stands. If you said 1, you were applying "follow the newest jq", which is the rule this section set aside: a 1.7.1 user's program, with a comment that happens to end in a backslash, would silently lose its + 2. If you were unsure, that is the right instinct: the decision does not depend on which answer looks better, only on what upstream says the change was.jq 1.7.1 does have a narrow special case for a backslash comment: skip_shebang drops the first three lines of a -f file that opens with the shell/jq polyglot. succinctly implements that rule too (#7481).

There is a third kind of change in 1.8.2: hard limits. jq 1.8.2 refuses, for example, to compare two values nested more than 10,000 levels deep, a security fix (CVE-2026-47770) that protects its C implementation's memory safety:

jq -n 'def deep: reduce range(10001) as $_ ([]; [.]); deep == deep'
jq 1.8.2's cap refuses an input that 1.7.1 and succinctly answer correctly.
Resultjq 1.7.1jq 1.8.2succinctly jq 0.8.0
stdouttrue(nothing)true
stderr(nothing)jq: error (at <unknown>): Equality check too deep(nothing)
exit status050

Here 1.7.1's answer is not a bug: true is correct. The cap guards a C program's memory safety, and succinctly, which answers correctly and has its own guard against running out of native stack, would gain no safety by adopting it, only lose capability. So it is not adopted, and the limitations page records all five of 1.8's new limits of this kind as deliberate differences from 1.8.2.

The whole rule, in order

Put the three sections together and you get a short procedure. It is applied in this order, to every behaviour where the candidates differ.

  1. Does matching jq 1.7.1 meet one of the four conditions? Output jq cannot read back, corrupted or discarded data, a crashed process, or no portable way to express it. Then refuse jq's behaviour and record the divergence. (The dropped [2].)
  2. Did upstream fix the 1.7.1 answer as a bug in 1.8.2? Then give 1.8.2's answer and record it as newer than the pin. (last(empty).)
  3. Otherwise, match jq 1.7.1 exactly, including its error messages and its own inconsistencies. (The swallowed x, and the comment that does not continue.)
  4. Only when two options are equally faithful, choose the faster one or the one that uses less memory. This step can never create a divergence, because it only ever chooses between answers that match.

Steps 1, 3 and 4 are ADR-0018's decision order (its #2416 amendment). Step 2 is how the limitations page applies it to jq's own later releases: an upstream bug fix is adopted, while a feature, a refactor or a rewording is not.

How it is checked

A rule like this is only worth as much as the checking behind it. succinctly's comparison harness, succinctly dev compare jq, measures it against a source build of jq 1.7.1. The four counts below are the same in its committed reports from an AMD Ryzen 9 7950X, an AWS Graviton4 (ARM Neoverse-V2) and an Apple M4 Pro.

446 / 447jq 1.7.1's own jq.test cases
224 / 224man.test, the manual's examples
5,894 / 6,000fuzzed programs that agree
65ledger entries; 0 unlisted, 0 stale
  • jq's own test suites. jq 1.7.1 ships test files, and the harness runs them through both tools. Besides the two above: onig.test (regular expressions) 39 of 40, base64.test 7 of 7, manonig.test 17 of 17 and optional.test 3 of 3. Both misses are cases where succinctly follows a 1.8 bug fix: jq.test's fromjson | isnan on "nan1234", which 1.8 rejects (CVE-2024-53427), and an optional group in an empty regex match, which 1.8 reports as unmatched. Against jq 1.8.2's suites it is informational only: 488 of 1.8.2's 550 jq.test cases agree. The rest test what 1.8 changed on purpose: how far as and unary minus reach, new builtins such as add(f) and trimstr, and the depth limits above.
  • Probes of the whole surface. Of the 218 builtins jq 1.7.1 lists, 207 are probed and 201 agree; there are also 1,097 syntax probes (1,090 agree) and 490 command-line probes, from --indent to locales. Separately, 308 of 308 error-message probes are byte-identical to jq's, because a message is part of what a program sees: try f catch (if test("Cannot index") then …) is a real jq idiom.
  • Grammar fuzzing. Three fixed seeds generate 2,000 random programs and documents each, and every result is compared on exit status, standard output and the class of any fault.
  • The ledger. Every difference the harness finds must be listed in comparison/jq/divergences/, one file per entry, with a category and a reason. The run fails on a difference that is not listed, and on a listed one that no longer differs, so the list cannot drift from the truth in either direction.

Ducky asks

5,894 out of 6,000 is 98%. So the fuzzer finds succinctly wrong on 2% of programs?

No. Of the 106 programs that do not count as agreeing, 104 were skipped: jq refused to compile them, or one tool timed out, and a generator's mistake is not evidence. The other 2 are real differences, and both are rows you have already seen: one is last of an empty generator, the other a foreach whose initial value is a generator, which jq 1.8 also fixed as a bug. Both are in the ledger as newer than the pin, and the run would fail if a finding were not.

Edge cases worth knowing

Compatible does not mean identical on every host

jq calls the platform's C library for maths and dates, and so does succinctly. Apple's and glibc's libm disagree in the last bit on many ordinary tan inputs, so a float digit from a maths builtin is a fact about a platform, not only about a jq version. succinctly matches the jq on the same platform, not one golden answer for all of them.

  • Deep recursion is refused, not run. A user-defined function that recurses 10,000 deep runs in jq (in about 3 seconds); succinctly's native-stack guard refuses it with exceeded maximum recursion depth rather than risk the process. It is in the ledger as by-design.
  • Less validation is a separate trade-off. succinctly reads JSON through a structural index rather than a full parse, so a filter checks only the parts of the text it reads. How succinctly reads JSON explains why, and --validate checks the whole text first when you need that.
  • succinctly yq is a preview. Everything on this page is about the jq mode. The yq mode aims at yq v4.53.3 under the same rule, with its own limitations page.

Your turn

Without scrolling back: what are the questions, in order, that decide whether succinctly jq gives jq 1.7.1's answer? Say them to yourself, then compare with the procedure above.

Now apply them to two cases this page has not shown. The facts about upstream are given; the answer is yours.

  • "1\u00002" | tonumber (a NUL inside the string): jq 1.7.1 prints 1, reading up to the NUL. jq 1.8.2 refuses the string, and its release notes list "Fix tonumber and toboolean to reject strings with embedded null bytes".
  • "abc" | split("b"; empty) (a flags argument that yields nothing): jq 1.7.1 prints ["abc"]; jq 1.8.2 prints nothing, after a commit titled "Refactor splits/2 using foreach syntax".
Predict: for each of the two, does succinctly jq give 1.7.1's answer or 1.8.2's?
Programjq 1.7.1jq 1.8.2succinctly jq 0.8.0
"1\u00002" | tonumber1string ("1\u00002") cannot be parsed as a number, exit 5string ("1\u00002") cannot be parsed as a number, exit 5
"abc" | split("b"; empty)["abc"](nothing)["abc"]

tonumber follows 1.8.2; split stays with 1.7.1. Neither matching 1.7.1 here corrupts data or crashes, so step 1 does not apply to either, and step 2 decides. Upstream calls the tonumber change a fix, so it is adopted (#7521). It calls the split change a refactor, so the pinned answer stands, even though 1.8.2's looks tidier (#7560). If you picked 1.8.2 for both because both look like improvements, that is the "follow the newest" model again: the rule asks what upstream said the change was, not which answer you prefer. If you picked 1.7.1 for tonumber because the NUL looked like data loss, look again at the dropped [2]: there a whole value vanished from the input, here the string is the input and jq 1.7.1 reads part of it, which is why this one is decided by step 2 rather than by step 1.

The next time a jq replacement, or any drop-in tool, says it is compatible, these are the questions to ask it: compatible with which version, by which rule, and where is the list of every place it is not?
