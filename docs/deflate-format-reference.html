The decoder's inner loop runs the join backwards. Its two tables are the two alphabets:

while True:
    sym = read_code(lit_len_table)    # literal, length or end
    if sym < 256:
        out.append(sym)               # a literal byte
    elif sym == 256:
        break                         # end of block
    else:
        i = sym - 257
        length = LENGTH_BASE[i] + read_bits(LENGTH_EXTRA[i])
        d = read_code(distance_table) # always follows a length
        distance = DIST_BASE[d] + read_bits(DIST_EXTRA[d])
        for _ in range(length):       # byte by byte: may overlap
            out.append(out[-distance])

Everything in the stream that isn't a symbol

Parts 1 and 2 introduce each part of a stream where it is needed. To read a stream yourself, or to write a decoder, you need them in one place, with one rule for how each is written. A DEFLATE stream is mostly Huffman codes, but not entirely. Bits are written in two ways, and a decoder must know which kind comes next:

  • A Huffman code is read one bit at a time, most significant bit first, because the decoder walks down the code tree as each bit arrives.
  • Everything else is a plain number of a fixed, known width, read lowest bit first. Each byte of the stream fills from its lowest bit up, so a plain number's bits arrive in the order they are packed.

In other words, DEFLATE is little-endian throughout, at the level of bits and of bytes (a stored block's 16-bit LEN comes low byte first), except that Huffman codes are stored bit-reversed. Write a byte the usual way, most significant bit on the left, and its plain fields read as ordinary binary, stacked from the right. Here is the first byte of part 2's dynamic block:

0 1 1 1 0 | 1 0   | 1
HLIT      | BTYPE | BFINAL
= 14      | = 2   | = 1

A Huffman code reads correctly in arrival order instead, so in this byte view it would look reversed. Decoders such as zlib reverse each code once, when they build their lookup tables, so that one little-endian bit reader can handle everything.

Everything else in the stream is a Huffman code: the literal/length and distance symbols, and, inside a dynamic block's header, the code-length symbols. The worked example's 103 bits show both kinds side by side in the bit walk.

Nothing in the stream says how long a field is. The decoder always knows what comes next and how big it is, in one of three ways:

  • A width fixed by the RFC, chosen to fit the field's range: BFINAL, BTYPE, HLIT, HDIST, HCLEN, the 3-bit code-length-code lengths, and a stored block's LEN and NLEN. After BTYPE = 2, the next 5 bits are HLIT because the format says so.
  • A width set by the symbol just decoded: the extra bits. Symbol 270 is always followed by 2 extra bits, d6 by 2, run symbol 18 by 7.
  • No width at all: Huffman codes end themselves. The decoder reads one bit at a time until the bits so far match a code, and since no code is the start of another, it can never stop in the wrong place.

That is why the stream needs no separators or length prefixes, and also why it must be read strictly in order: where HDIST starts depends on having read HLIT, and one corrupted bit misaligns everything after it.

Edge cases

Overlapping copies
Allowed and common: distance 1 with length 258 repeats the previous byte 258 times. A decoder must copy byte by byte, not with a block copy, or it reads bytes that haven't been written yet.
The longest match
258 bytes, with its own symbol (285) and no extra bits, so with the fixed codes a long run costs 13 bits per 258 bytes. 258 = 255 + 3: a length fits in a byte once the minimum of 3 is subtracted.
End of block
Symbol 256 ends every Huffman block, even the last. It needs a code, so it counts as a symbol when the tree is built.
Empty input
zlib writes 2 bytes, 03 00: a final fixed block holding only the end-of-block code.
Incompressible input
Stored blocks cap the overhead at 5 bytes per 65,535. A large file of random bytes grows by under 0.01%; the 1 KiB in the chart grows by 0.5%.

Terms used on this page

These are defined here, for this series. DEFLATE's broader terms are in the site glossary: DEFLATE, LZ77, Huffman code, canonical Huffman code, back-reference, sliding window, end-of-block and extra bits.

Alphabet

The fixed set of symbols a Huffman code is built over. DEFLATE uses three: literal/length, distance and code-length. How the two ideas join

BFINAL

The first bit of every block: 1 if it is the last block of the stream. Blocks, and the fixed code

BTYPE

The 2 bits after BFINAL that give the block type: 00 stored, 01 fixed Huffman codes, 10 dynamic Huffman codes. 11 is invalid. Like every plain number, they arrive lowest bit first. The values

Code length

The number of bits in a symbol's Huffman code. 0 means the symbol has no code. A dynamic block sends only the lengths; the codes follow from them by the canonical rule. Send lengths, not trees

Code-length code

The small Huffman code a dynamic block uses to write down its code lengths. Its alphabet has 19 symbols: 0–15 are lengths, 16 repeats the previous length, and 17 and 18 are runs of zeros. CL is short for code length. Huffman-code the run symbols

Distance alphabet

The 30 symbols, d0–d29, that stand for back-reference distances from 1 to 32,768. Most stand for a range, picked out by extra bits. It has a Huffman code of its own. How the two ideas join

Dynamic Huffman code

Codes built for one block from that block's own symbol counts, and sent as code lengths at its start (BTYPE 10). They don't change while the block is read: dynamic means per block, not adaptive. A dynamic block, bit by bit

Fixed Huffman code

Codes set once by the RFC, for any block with BTYPE 01, so no table is sent: 8 or 9 bits per literal, 7 or 8 per length symbol, 5 per distance symbol. Why 7–9 bits

HCLEN

4 bits in a dynamic block's header: how many code-length-code lengths follow, minus 4. Those lengths come in a fixed order, so the count can cut off the usually-unused ones at the end. Why that order

HDIST

5 bits in a dynamic block's header: how many distance code lengths follow, minus 1. In the bit walk

HLIT

5 bits in a dynamic block's header: how many literal/length code lengths follow, minus 257. The lengths come as a bare list in symbol order, so the count says where the list ends. In the bit walk

Literal

A byte that LZ77 sends as itself, because no match of 3 or more starts there. It becomes the literal/length symbol with the same value, 0–255. LZ77

Literal/length alphabet

The 286 symbols 0–285: 0–255 for literal bytes, 256 for the end of the block, and 257–285 for ranges of lengths. One Huffman code covers them all, so a single code says whether a literal or a copy comes next. How the two ideas join

Overlapping copy

A back-reference whose length is greater than its distance, so it reads bytes it is itself writing. It works because the decoder copies one byte at a time; distance 1 simply repeats a byte. The bit walk shows one

Plain number

A field of fixed, known width that is not Huffman-coded, read lowest bit first: the block header, the extra bits, a dynamic block's counts and code-length-code lengths, and a stored block's LEN and NLEN. Every plain field

Prefix code

A code in which no codeword is the start of another, so codes can be read back to back without separators. Every Huffman code is a prefix code. Huffman

Stored block

A block of up to 65,535 raw bytes (BTYPE 00), after a byte-aligned length and its complement. Encoders use it when compressing would make the data bigger. Choosing a block type

Symbol

One element of an alphabet: what Huffman coding counts and gives a code. DEFLATE maps LZ77's tokens onto symbols, so Huffman coding never sees the raw bytes. How the two ideas join

Token

One item of LZ77's output: a literal, or a back-reference (length, distance). Each becomes one or two symbols. LZ77
