How a DEFLATE block sends its own code

A Huffman code fitted to the text saves bits only if the decoder can be told what it is, and telling it costs bits too. This page takes that description from 1,264 bits down to 159, and shows why a block sends nothing but code lengths.

  • A block that fits its own Huffman code sends only each symbol's code length, in symbol order. The decoder rebuilds exactly the same codes from the lengths, by a rule both sides know.
  • It matters because the description is pure overhead: for a 381-byte paragraph, the fitted code saves 854 bits on the data and describing it costs 352.
  • The common misconception is that the Huffman tree travels with the data. It doesn't: no tree and no symbol names are sent.

Where part 1 left off

Part 1 built DEFLATE's two savings and read a block written with the fixed codes, which the format sets once, so a block never has to describe them. The one idea to bring from it: a code fitted to a block's own counts saves bits on the data, but the decoder has never seen those counts, so the block has to tell it the code. For a 381-byte paragraph of English, the fitted code saved 854 bits on the data, and describing it cost 352 of them. Describe it carelessly and the code costs more than it saves.

This page is about that description. First we fit a code to part 1's 35-byte example, abracadabra abracadabra abracadabra, so there is something concrete to send. Then we look for the cheapest way to send it: as a table, as a tree, and then the idea that makes DEFLATE's dynamic blocks affordable, sending nothing but code lengths. The rest of the page squeezes that list of lengths from 1,264 bits to 159, and ends by reading a whole dynamic block bit by bit.

The example's own code

Fitting a code pays for the paragraph. To follow one all the way through, here is the code fitted to the 35-byte example. Huffman coding never sees the raw letters: it counts the symbols that LZ77's output maps to (the join). After LZ77 the example is 10 tokens plus the end-of-block symbol: 11 symbols, 9 of them different. a appears 3 times, as a literal; every other symbol appears once.

Count the symbols. The 8 literals, the two length symbols 258 and 270, and end-of-block. With the fixed code these 11 symbols cost 85 bits.

Join the rarest, in pairs. Eight symbols tie at 1. Joining two at a time, lowest symbol number first, makes four nodes of 2: ␣ with b, c with d, r with end, 258 with 270.

Again. The four nodes of 2 pair up into two nodes of 4.

Now a is one of the two rarest. With 3 it is lighter than either 4, so it joins one of them to make 7.

The last join makes the root, 11: every symbol.

Read the codes. Label each left branch 0 and each right branch 1. A symbol's code is the path from the root to it: a is 10, r is 000, ␣ is 1100. No code is the start of another, because every symbol is a leaf.

Count the bits. A code's length is the symbol's depth in the tree: a has 2 bits; r, end, 258 and 270 have 3; ␣, b, c and d have 4. The 11 symbols now cost 34 bits instead of 85.

As a table. The tree has done its job. What remains is each symbol with its code and its length, in the order of the tree's leaves. The next section starts from exactly this table.

The distance code is simpler: d5 and d6 are used once each, so each gets 1 bit. This code takes the example's symbols from 85 bits to 34. But the decoder has never seen the example's counts, so it can't build the tree itself: the block has to tell it the code, and every bit spent on that comes out of the 51 bits saved.

Send lengths, not trees

How should a block tell the decoder its code? The most literal way is a table. For each used symbol, write its number in 9 bits, enough for all 286 literal/length symbols, then its code's length in 4 bits so the decoder knows where the code ends, then the code itself. For the example that is 9 × (9 + 4) bits plus the 30 bits of the codes, 147 bits, and d5 and d6 add 2 × (5 + 4 + 1) = 20: 167 bits, plus something to say where the table ends. That is four times the 41 bits of data it describes, and more than three times the 51 bits the code saves.

Sending the tree is cheaper, because the codes are implied by its shape and need not be written out. Walk it from the root, left branch before right. At a branch write 0; at a leaf write 1, then the leaf's symbol number. The decoder rebuilds the same tree from those bits: a 0 means two subtrees follow, a 1 means a symbol follows. Against the example's tree, the walk starts 0 0 0 1 r: the root, the node of 4 on its left, the node of 2 on that one's left, then the leaf r, followed by its sibling, 1 end.

That is 111 bits for the example. Look at where they go: 20 describe the shape, and 91 name the symbols. Neither is what the decoder actually needs.

  • The names. The tree needs them because its leaves come in tree order, so each leaf must say which symbol it is. A list in symbol order needs none, because the decoder counts as it reads: the first length is symbol 0's, the second symbol 1's, so the 98th is symbol 97's, which is a's. Nothing in the stream says 97; the position does. Below is the whole trip, from that slot to the byte a.
  • The shape. As the tie-break question in part 1 showed (when nodes tie, joining a different pair gives a different tree with the same total), many trees are equally good. Swap the two halves under the node of 7: a becomes 11, and ␣, b, c and d become 1000 to 1011. Every one of those codes changes, but no length does, so the data still costs 34 bits. The tree spends bits picking one code out of many that are all as good.

So DEFLATE drops both, and this is the step the rest of the page builds on. It fixes one rule for turning code lengths into codes, called the canonical Huffman code, so no shape is sent. And it sends the lengths as a list in symbol order, so no symbol is named.

Start from the tree's codes, in the order of its leaves: r 000, end 001, 258 010, 270 011, a 10, then ␣, b, c and d 1100 to 1111.

Throw the codes away. Keep only each symbol's length. This is all a DEFLATE block sends.

Sort by length, and by symbol number within a length: a (97); then r (114), end (256), 258 and 270; then ␣ (32), b, c and d.

The first code is all zeros, as long as the shortest length: a gets 00.

Count up, then shift. Add one to the last code (01), then append a 0 for the extra bit of length: r gets 010. Within a length, count up: end 011, 258 100, 270 101.

Again for 4 bits. 101 + 1 is 110, and one more bit makes ␣ 1100; then b 1101, c 1110, d 1111. The decoder runs the same rules on the same lengths, so it gets the same codes without ever seeing a tree.

These are not the tree's codes: a was 10 and is now 00, and r was 000 and is now 010. But every symbol keeps its length, so the 11 symbols still cost 34 bits. Counting up keeps the code prefix-free: only a's code starts 00, and only the 4-bit codes start 11. The distance code works the same way: d5 and d6, 1 bit each, get 0 and 1. These are the codes the example's dynamic block uses, in the bit walk further on.

You might object that we have swapped 11 symbol names for something worse: a length for every symbol a block could use, 316 of them, used or not. You would be right, and squeezing that list is the rest of this page. But if you stop here, you already have the core of it: a dynamic block sends code lengths, the decoder rebuilds the codes from them by counting, and no tree and no symbol name is ever sent.

Decoding with only the lengths

Before we measure what the list costs, a short detour: how does a decoder get from a bare list of lengths to the right bytes, without any symbol ever being named? If you are happy to trust that it can, skip ahead to the cost. The one thing to take from this section is that the decoder turns the lengths into a lookup table, then decodes each symbol with a single lookup. For a, the whole trip is three steps:

  1. Its slot. The decoder counts the lengths as it reads them. Slot 97, the 98th length, is a's because a is symbol 97, and it holds 2.
  2. Its code. Once it has every length, the decoder runs the canonical rule above and builds a lookup table from code to symbol. a is the only symbol of length 2, so it gets 00, as it did in the encoder.
  3. Its byte. In the data, the decoder reads 00, looks it up and gets symbol 97. A symbol below 256 is a literal, so it outputs byte 97, 01100001: a.

Step 2 is where the work is. The codes are 2, 3 and 4 bits long, and nothing in the data marks where one ends, so the decoder can't simply cut the data into codes. It could read one bit at a time and check, after each, whether the bits so far make a code: up to 4 checks per symbol here, and up to 15 in a block with 15-bit codes. Instead it builds a table that answers both questions at once: given the next few bits, which symbol do they start with, and how many bits is its code? Here it is for the example, from start to finish: from the lengths the block sent, to its codes, to its table, and then the table at work on the example's own data.

Start from what the block sent: one length per symbol, in symbol order, 271 of them. The decoder knows each one's symbol by counting: the 98th is symbol 97, a, and it is 2. 262 of the 271 are 0, unused; they are folded into ranges here. Only 9 symbols have a code.

Turn the lengths into codes, by the canonical rule: sort the 9 used symbols by length, then by symbol number, and count up. a, the only length 2, gets 00; the four 3s get 010 to 101; the four 4s get 1100 to 1111. The encoder did the same, so these are its codes.

Fill a's entries. The longest code is 4 bits, so the table has one entry for every 4-bit pattern: 24 = 16. a's code, 00, is only 2 bits. Any 4 bits that start 00 begin with a, whatever the other two are, so a fills all four entries from 0000 to 0011. Each one says: a, 2 bits.

The longer codes fill fewer entries. Each 3-bit code fills two: r 0100 and 0101, end 0110 and 0111, 258 1000 and 1001, 270 1010 and 1011. Each 4-bit code fills one, ␣ to d, 1100 to 1111. That makes 4 + 4 × 2 + 4 × 1 = 16: every entry is filled exactly once, so any 4 bits the decoder meets begin with exactly one code.

Decode: peek at 4 bits. The data starts 0011. Entry 0011 says a, 2 bits. The decoder outputs a and consumes only those 2 bits: the other two are the start of the next code.

The window moves on by 2. The next 4 bits are 1101: b, 4 bits. Output b, consume 4.

0100: r, 3 bits. The decoder always peeks at 4 bits, and the entry says how far to move. It never needs to know in advance where a code ends.

Four more lookups: 0011 a, 1110 c, 0011 a, 1111 d. Output so far: abracad.

1000: 258, 3 bits. The last of those 4 bits isn't 258's: it was peeked at, not consumed. 258 is not a byte but a copy length, 4, so a distance comes next, looked up in the distance table, built the same way from the block's two distance lengths: 0 is d5, and its extra bit, 0, makes the distance 7. The decoder copies abra from 7 bytes back: abracadabra.

So a decoder builds its lookup tables itself, at the start of every dynamic block, from the lengths the block sends. It builds one for literals and lengths and one for distances, and (as the sections below show) one more before those, to read the lengths themselves. Only then can it read the data. A new dynamic block brings new lengths, so the tables are built again. A fixed block's lengths never change, so its tables are built once and reused.

Go deeper: what zlib's tables look like

A decoder could follow the code one bit at a time, but zlib looks up several bits at once. Its literal/length table is indexed by the next 9 bits of input, 29 = 512 entries, or fewer bits when no code is that long. Each entry holds the symbol and how many of those bits its code really used; the decoder consumes only that many. A short code fills several entries: in a 9-bit table a 2-bit code fills every entry that starts with its two bits, 128 of them. A code longer than 9 bits points to a second, smaller table for its remaining bits. The distance table works the same way with 6 bits, and the code-length table with 7, enough for its longest code. zlib also stores each code reversed, to match the order bits arrive in.

That is the end of the detour. Back to the objection from the end of the last section: dropping the names has a price. A list in symbol order has a slot for every symbol a block could use, not just the ones it does, so it starts out far longer than the tree. The next section measures how much longer, and shrinks it.

Sending a dynamic code

A dynamic block must tell the decoder its codes before its data. Thanks to canonical codes, it only needs to send each symbol's code length: 286 literal/length symbols and 30 distance symbols, 316 lengths in all, each from 0 to 15. The question is how to send them cheaply, and it matters: every bit spent on the code comes out of the saving. For the paragraph, the fitted code saved 854 bits on the data, and sending it cost 352 of them. Here are four tries, each fixing the biggest waste in the one before, measured on two blocks: the worked example written as a dynamic block (the one walked through below), and zlib's real block for the 381-byte paragraph.

Step 1: every slot, 4 bits. All 316 of the example's code lengths, in symbol order. Only the 11 marked slots are not zero. 1,264 bits.

Step 2: say how many. HLIT and HDIST cut each list after its last used symbol, 270 and d6, so 38 slots go. 1,122 bits: the zeros in the middle are still there.

Step 3: runs. Each stretch of zeros collapses into one run symbol: 18 for 11–138 zeros, 17 for 3–10. Each used length becomes one symbol too. The fans show which stretch of the old list each chip replaced.

Read each column down. Symbol sent is what goes in the stream; stands for is what it means (×32 is a run of 32 zeros, a is a's length); extra bits follow a run symbol and give its count as a plain number, least significant bit first, counted from the shortest run the symbol allows. Under the first 18, 1010100 read backwards is 0010101, 21, and 18's runs start at 11, so 11 + 21 = 32. bits is what it costs: 5 for the symbol, plus its extra bits, so an 18 costs 5 + 7. 19 symbols come to 146 bits.

Step 4: code the run symbols. 18, 3 and 4 get 2-bit codes, 17 gets 3 bits, 1 gets 4, and 0 and 2 get 5. With the 54 bits that describe this code, that makes 159 bits: for this short list, 13 more than step 3.

1. Every length, 4 bits each

Write all 316 lengths as plain 4-bit numbers, in symbol order. That is 1,264 bits, 158 bytes, in every dynamic block whatever it holds. The example's data is only 41 bits, so its code table would cost 30 times as much as the data it describes. Even the paragraph's data, 1,521 bits, would nearly double. It is also more than ten times the tree's 111 bits for the example: the tree pays about 11 bits for each symbol a block uses, but the list pays 4 bits for every symbol it could use. Steps 2 to 4 cut what the unused ones cost.

2. Say how many

Any one block uses few of the symbols. So send two counts first, how many literal/length lengths follow and how many distance lengths (plain 5-bit numbers the format calls HLIT and HDIST), and stop each list after its highest used symbol; the rest count as 0.

Guess before you read on: the example uses only 11 of its 316 symbols. How much should cutting each list after its last used symbol save?

Hardly anything. It barely helps: 1,122 bits for the example and 1,158 for the paragraph, against 1,264. The unused symbols are mostly in the middle of the alphabet, the byte values a text never contains, not at the end, so there is little tail to cut.

The counts stay in the final scheme anyway: with no separators, they are how the decoder knows where each list ends. To shrink the list, step 3 has to deal with the zeros in the middle.

Runs, and a code for the runs

3. Replace runs with one symbol

Write the lengths with a small alphabet of 19 symbols instead: 0–15 for a length, 16 to repeat the previous length, and 17 and 18 for runs of zeros, each followed by plain extra bits that give the count. For now, write each of these symbols as a plain 5-bit number. A whole stretch of unused byte values becomes one symbol: the example's 262 unused literal/length symbols take just 7. The header drops to 146 bits for the example (step 3 in the figure) and 443 for the paragraph. That is the big win, but the paragraph's header is still 443 bits.

4. Huffman-code the run symbols

Step 3 still spends 5 bits on every run symbol, yet they are far from equally common. Of the paragraph's 78, the lengths 8 and 5 appear 14 times each and 0 appears 12 times, while 2 appears once and 16 not at all. That is the same skew Huffman coding removes from the data, one level down, so DEFLATE gives these symbols a Huffman code too: the code-length code, a Huffman code whose job is to send the other two codes. Its own 19 lengths go first, as plain 3-bit numbers. A dynamic block is therefore a stack of three layers, each written with the one below it:

It stops at three layers because the bottom one is so small: 57 bits at most, too little for yet another code to repay its own description. This is DEFLATE's actual scheme, and it costs 159 bits for the example (step 4 in the figure) and 352 for the paragraph. For the paragraph, coding the run symbols saved another 91 bits. For the tiny example it cost 13 more: describing the small code took more than it saved on just 19 run symbols. DEFLATE has no way to stop at step 3, which is one more reason tiny blocks are written with the fixed codes.

And against the tree? For the example, the tree still wins, 111 bits to 159: a block with only 11 different symbols has too few names to be worth dropping. For the paragraph, which uses 46 literal/length symbols and 11 distances, the tree would cost 581 bits, 469 of them names, against 352 for the lengths. Real blocks run to thousands of symbols and use far more of the alphabet, so the gap only grows.

What changes from block to block is only which of the 19 symbols a block uses, and the code each one gets: in the worked example below, symbol 18 is 10 and 16 isn't used at all, but 18 still means 11–138 zeros with 7 extra bits. For the 381-byte paragraph, zlib's whole header (HLIT = 270, HDIST = 17, HCLEN = 16, then the lengths) is 352 bits, about 44 bytes. That is the price of the table, and the paragraph is long enough to repay it.

The code-length code's 19 lengths are sent in a fixed order, 16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1, 15, and HCLEN (4 bits) says how many are sent; any not sent count as 0.

Go deeper: why that order?

The order is a bet on which code lengths a block will use, most likely first, so that HCLEN can cut off the unlikely ones. The RFC lists it without a reason, but it reads in four parts:

  • 16, 17, 18: the repeat and zero-run symbols, which nearly every dynamic block uses to skip the byte values it never sees.
  • 0: every block has unused symbols.
  • 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1: outward from 8, because with 286 symbols most codes come out around 7–9 bits, and very short or very long codes are rare.
  • 15 last, the rarest of all.

For the paragraph, zlib's codes use lengths 2 to 8, so HCLEN is 16 and the last three, 14, 1 and 15, are never sent.

The block header. BFINAL is 1. BTYPE arrives as 0, then 1: binary 10, a dynamic block. Every code from here on is defined by the block itself.

How many lengths follow. The code lengths come next as a bare list in symbol order: the first is symbol 0's, the second symbol 1's, with no symbol numbers and nothing to mark where the list ends and the data begins. So the block says first how long each list is. HLIT: 271 literal/length lengths, for symbols 0–270. 270 is the highest symbol this block uses, so the encoder stops there and leaves out 271–285. HDIST: 7 distance lengths, d0–d6. HCLEN: 18 of the 19 code-length-code lengths. The names are the RFC's: they count the literal/length, distance and code-length codes. The RFC never says what the H stands for, though it is usually read as Huffman.

All three are plain numbers, which arrive lowest bit first, so each line shows the bits the usual way round as well: 0111 arrives, read backwards that is 1110 = 14, and HCLEN stores the count minus 4.

The code-length code. CL is short for code length: the code-length alphabet has 19 symbols, 0–18, used to write out the code lengths that follow, and each of these lines gives the length of one of their codes. There are 18 plain 3-bit lengths, in the fixed order 16, 17, 18, 0, 8, 7, 9, 6, 10, 5, 11, 4, 12, 3, 13, 2, 14, 1. In this block, they define a small Huffman code over the code-length symbols: 3, 4 and 18 get 00, 01 and 10; 17 gets 110; 1 gets 1110; 0 and 2 get 11110 and 11111. Symbol 15 is unused and would come last, so HCLEN leaves it off.

In this block, 11 of these 18 lengths are 0, and each costs the full 3 bits: 33 bits that only say "unused". This list is the bottom of the stack, with no code of its own, so unlike the lists that follow, its zeros can't be run-length coded. All the format can do is put the usually-unused symbols last, so that HCLEN cuts off the zeros at the end. Here most of the unused symbols come before 4, 3, 2 and 1, which are used: the order bets on lengths near 8, as in a typical block, but this block's codes are only 1 to 4 bits long, so the bet loses.

271 literal/length code lengths, in 16 code-length symbols. Runs of zeros cover the byte values this text never uses: one 18 and its 7 extra bits cover 138 of them, the most any one run can. In this block only 9 symbols get a length: a gets 2 bits; r, end-of-block, 258 and 270 get 3; ␣, b, c and d get 4. Symbol 257 sits between used symbols, so its zero is written on its own, for 5 bits.

A length of 0 means the symbol gets no code. It costs nothing in the data, and the decoder skips it when it builds the codes, which is what lets the 9 used symbols share all of the code space. But the list still needs a 0 in its place, because position is the symbol number.

7 distance code lengths. Five zeros for d0–d4 (symbol 17 and 3 extra bits), then d5 and d6 get 1 bit each. That ends the header: 159 bits after BTYPE to describe both codes.

The data, in this block's own codes. From the lengths alone the decoder builds this block's canonical codes: a = 00; r = 010, end = 011, 258 = 100, 270 = 101; ␣ = 1100, b = 1101, c = 1110, d = 1111. So a costs 2 bits here, against 8 with the fixed code.

The copies. Length symbol 258 is 100, with no extra bits. Only two distance symbols are used, so d5 is just 0, then its 1 extra bit picks 7. (23, 12) is 270 (101) and 2 extra bits, then d6 (1) and 2 extra bits. The extra bits are exactly what a fixed block would carry: they are never Huffman-coded.

End of block is 011, and 5 bits of padding fill the 26th byte. The data took 41 bits, against 100 in the fixed block, but describing the codes took 159. So for this string the fixed block wins, as zlib decided; on longer text the table costs about the same while the savings keep growing.

Go deeper: isn't sending all those zeros wasteful?

Per symbol, less than it looks. In this block, the literal/length list describes 271 symbols in 77 bits: its 262 zeros take 56 bits, as 6 runs and one lone zero, and the 9 used lengths take 21. Listing only the used symbols instead would need a 9-bit symbol number and a 4-bit length for each, 117 bits before even saying how many there are. A run of zeros is really a way of saying "skip ahead", and because those runs are Huffman-coded too, the common skips are the cheap ones. The more symbols a block uses, as ordinary text does, the further ahead the positional list gets.

In a block this small, though, saying "unused" is most of the header: 95 of its 159 bits. Besides those 56, 6 bits mark d0–d4 as unused, and 33 go on the code-length code's own list, where 11 of the 18 lengths are 0 at 3 bits each, because that list has no code to compress it. These costs barely grow with the block, which is why tiny blocks stay fixed: in a full-size block of text the whole table is typically under 1% of the output. DEFLATE's real inefficiency is that every dynamic block sends a complete new table, even when the last block's code would do; later formats can reuse it, as Zstandard does with its "treeless" literals blocks (RFC 8878 §3.1.1.3.1.1).

Choosing a block type

An encoder now has a choice for every block, and it matters. The example's dynamic block is twice the size of its fixed one, while the paragraph's dynamic block is a fifth smaller than its fixed one. And for data with no repetition or skew, such as random bytes, both codes make things worse: the fixed code spends 8 or 9 bits on every byte. That is what the third type, the stored block, is for: it copies the bytes as they are. Here are the three side by side.

Stored (00)

No compression: up to 65,535 raw bytes after a 4-byte length and its complement.

  • Caps the cost of incompressible data at 5 bytes per 64 KiB
  • No saving at all

Fixed Huffman (01)

Codes set by the RFC: 8 or 9 bits for a literal, 7 or 8 for a length, 5 for a distance.

  • No table to send
  • Wins on short inputs
  • Ignores this data's skew

Dynamic Huffman (10)

Codes built for this block's own counts, sent as code lengths at the start of the block.

  • Removes the skew too
  • Usually wins once a block holds more than a few dozen bytes of text
  • The table costs tens of bytes

Any input can be written as any of the three, and every one is valid: a decoder accepts whichever it gets. Which one wins is a sum, not a rule. The encoder works out the exact size of each kind for every block (zlib ends a block after about 16,000 symbols) and writes the smallest. Tiny blocks come out fixed because a code table costs more than it saves: for the paragraph in the chart, zlib 1.2.12 switches from fixed to dynamic once the text is 74 bytes long.

What a block's code costs

Back to the paragraph from the start. Its fitted code saves 854 bits on the data, and the description that makes that possible costs 352: three counts and the code-length code's own lengths, then the 78 run symbols that spell out the code lengths. Sent as a tree, the same code would cost 581 bits; as a plain list of 316 lengths, 1,264, more than the whole saving. Each step on this page is what turned a code that doesn't pay into one that does.

The pattern is worth keeping, because it turns up wherever a format has to ship a model along with its data: send the least that determines the model (lengths, not codes), in an order the receiver can predict (position, not names), and compress the description with the same tool, one level down, until it is too small to repay another level.

DEFLATE's own limit is per block. Every dynamic block sends a complete new table, even when the previous block's would do. In a full-size block of text the table is typically under 1% of the output, so this matters little; for small blocks it is most of the block, which is why they stay fixed. Later formats can reuse a table across blocks, as Zstandard does.

Terms used on this page

These are defined here, for this page. DEFLATE's broader terms are in the site glossary: DEFLATE, LZ77, Huffman code, canonical Huffman code, back-reference, sliding window, end-of-block and extra bits.

Alphabet

The fixed set of symbols a Huffman code is built over. DEFLATE uses three: literal/length, distance and code-length. How the two ideas join

Code length

The number of bits in a symbol's Huffman code. 0 means the symbol has no code. A dynamic block sends only the lengths; the codes follow from them by the canonical rule. Send lengths, not trees

Code-length code

The small Huffman code a dynamic block uses to write down its code lengths. Its alphabet has 19 symbols: 0–15 are lengths, 16 repeats the previous length, and 17 and 18 are runs of zeros. CL is short for code length. Huffman-code the run symbols

Dynamic Huffman code

Codes built for one block from that block's own symbol counts, and sent as code lengths at its start (BTYPE 10). They don't change while the block is read: dynamic means per block, not adaptive. A dynamic block, bit by bit

Fixed Huffman code

Codes set once by the RFC, for any block with BTYPE 01, so no table is sent: 8 or 9 bits per literal, 7 or 8 per length symbol, 5 per distance symbol. Why 7–9 bits

HCLEN

4 bits in a dynamic block's header: how many code-length-code lengths follow, minus 4. Those lengths come in a fixed order, so the count can cut off the usually-unused ones at the end. Why that order

HDIST

5 bits in a dynamic block's header: how many distance code lengths follow, minus 1. In the bit walk

HLIT

5 bits in a dynamic block's header: how many literal/length code lengths follow, minus 257. The lengths come as a bare list in symbol order, so the count says where the list ends. In the bit walk

Literal/length alphabet

The 286 symbols 0–285: 0–255 for literal bytes, 256 for the end of the block, and 257–285 for ranges of lengths. One Huffman code covers them all, so a single code says whether a literal or a copy comes next. How the two ideas join

Prefix code

A code in which no codeword is the start of another, so codes can be read back to back without separators. Every Huffman code is a prefix code. Huffman

Stored block

A block of up to 65,535 raw bytes (BTYPE 00), after a byte-aligned length and its complement. Encoders use it when compressing would make the data bigger. Choosing a block type

Symbol

One element of an alphabet: what Huffman coding counts and gives a code. DEFLATE maps LZ77's tokens onto symbols, so Huffman coding never sees the raw bytes. How the two ideas join
