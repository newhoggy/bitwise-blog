Benchmarking against jq honestly

Lots of tools claim to beat jq. This is how succinctly's claim is measured: what gets timed, what has to match before a timing counts, how the tools take turns, how 223 ratios become one number, and how to tell a real slowdown from noise.

  • A faster-than-jq number means something only if the method rules out the usual ways benchmarks mislead. succinctly's comparison times no row whose output differs from jq 1.7.1's, interleaves the tools inside every repetition, and sums up 223 rows per chip with a geometric mean.
  • The reports behind 3.18x (AMD Ryzen 9 7950X), 3.10x (AWS Graviton4) and 2.84x (Apple M4 Pro) are committed with their provenance, and one script reruns the Graviton4 one on a fresh AWS instance. You can check them rather than trust them.
  • The common mistake: trusting a timing because its minimum and median agree. Drift during or between runs moves both together, so their agreement is necessary, never sufficient.

This page is the method behind the succinctly 0.8.0 announcement, which has the results. If you already run interleaved A/B comparisons with a control, skip to the release-day case study and see whether you'd have called it the same way.

What a faster-than-jq number has to survive

On an AMD Ryzen 9 7950X, succinctly jq 0.8.0 is 3.18x faster than jq 1.7.1: that is the geometric mean over 223 workloads.Every speed figure on this page is of the comparison harness's own build: a release build with the features cli,simd,regex,serde plus bench-runner, stripped. The release archives are built with cli alone, and no committed figure is of that build. You have probably seen numbers like that before, and learned to ask what they hide.

Benchmark claims tend to go wrong in one of four ways. Each of the next sections is the check for one of them:

  • The fast tool did a different job. It printed something else, or stopped early. The check is an output gate.
  • The machine changed between the tools' turns. The check is interleaving.
  • The workloads were picked to win, or a few huge wins carry the average. The check is many rows and a geometric mean, with the rows jq wins listed.
  • Noise was read as a result. The checks are an A/A′ control and instruction counts.

The page ends with a slowdown that showed up on release day, and the four checks at work on it.

What gets timed

The comparison is a subcommand of the succinctly binary, succinctly dev compare jq. Files in the repository drive it, not code: a manifest pins the reference builds and the inputs, and a table lists the queries.

With --full, it times 84 queries over 40 inputs: 223 query and input pairs, which the reports call rows.

  • 2 rows with no input (startup and args_many) measure start-up.
  • 106 rows at 1 MB, 73 at 10 MB and 42 at 100 MB run over generated documents of several shapes: users, nested, wide objects, strings, numbers, NDJSON and JSON text sequences. The 1 MB tier also holds seven real files from a benchmark corpus, all under 1 MB.
  • Reported apart: 24 rows that pipe the input on standard input, and, with --huge, six rows at 1 GB. Neither group moves the headline numbers.

Everything that could drift is pinned. jq 1.7.1, the reference, and jq 1.8.2, timed beside it, are built from source whose SHA-256 is in the manifest. The harness never uses the jq on your PATH. Every generated input is checked against its SHA-256 too. The run records the commit, CPU, OS, toolchain and build features in env.json. It marks itself INVALID if the tree is dirty, the machine is on battery, the build is not a release build, or its features differ from the manifest's.

Why three chips? Because memory-bound effects don't carry over from one CPU to another. One fix in this codebase (#106) measured 6.1x on an Apple M4 Pro and 16.4x on a Ryzen 9 7950X. So each chip gets its own report, and no figure here is carried from one chip to another.

First, the outputs must match

A timing compares two tools doing the same job, so the first thing the harness checks is that they did the same job.

The usual quick benchmark is hyperfine over two commands, which times whatever each command does. Suppose one of them printed a number in another format, skipped a record, or failed early with an error. Then you would be timing two different jobs, and a tool that does less is easy to make fast.

So before any timing, the harness runs each tool once on the row and keeps two things: its exit status, and the SHA-256 of everything it wrote to standard output. Then it compares succinctly's pair with jq 1.7.1's:

// Output-identity gate: hash each tool's stdout, compare with its exit status.
let mut digest = vec![];
for t in tools {
    let e = exec_digest(t, &args, feed.unwrap_or_default(), inputs_dir, deadline)?;
    // … (a deadline check)
    digest.push((e.exit, e.stdout_sha256));
}
let gate_of = |i: usize| {
    if huge && (ends[0].killed() || ends[i].killed()) {
        Gate::Incomplete
    } else if digest[i] == digest[0] {
        Gate::Match
    } else {
        Gate::Differs
    }
};

A row that differs stops there, before its first timed run. It gets no timing, and the report lists it as a correctness failure. jq 1.8.2 gets the same check, and a row where it disagrees only loses its 1.8.2 column. In the committed runs, all 223 rows matched jq 1.7.1 on all three chips, so every row has a timing.

Ducky asks

So matching output means succinctly checks the input as carefully as jq does?

No. The gate compares answers on these inputs, and the inputs are valid JSON, apart from the jsonseq-bad rows, which carry one truncated record on purpose. succinctly reads JSON by building a light index instead of a full tree, and it validates less than a full parser while doing it. How succinctly reads JSON covers that trade-off, and --validate for when you need strict checking. The gate makes a narrower promise: on every row it times, the two tools printed the same bytes and exited the same way.

Then, the tools take turns

With the outputs matched, the order you run things in can still decide the result.

The naive plan is to run jq 21 times, then succinctly 21 times, and compare the medians. This repository has a record of what that does. Running all of one binary and then all of the other made an improved binary measure 0.47-0.9x, up to 2x slower, on every workload. The second half started on a machine the first half had warmed up.

Ducky asks

Wouldn't more repetitions average that out?

No. Averaging cancels noise that goes both ways, and this drift goes one way: the later tool is always on the warmer machine. More runs only measure the bias more precisely. In that record, the minimum and the median agreed with each other, and both were wrong.

The fix is to take turns. In the naive order, each tool's position decides its conditions. In the interleaved order, each repetition runs every tool once and the starting tool rotates, so each one goes first, second and last equally often:

The loop is a few lines of the harness:

'reps: while rep < total {
    for k in 0..tools.len() {
        let i = (rep + k) % tools.len();
        let (ms, end) = time_once_ended(&tools[i], &args, inputs_dir, feed)?;

Before the loop, each tool gets one untimed warm-up run. A --full run gives start-up and 1 MB rows 21 repetitions, 10 MB rows 9 and 100 MB rows 3. A row whose slowest tool takes longer than 15 ms gets more repetitions, up to 21, but no more than 30 seconds of extra timed runs. A row that reaches the full 21 is rated by each tool's fastest run instead of its median, because the median of a long row moves with the run and its minimum does not. Rows whose run-to-run variation is over 5% are flagged as noisy in the report. Peak memory comes from separate, untimed runs, so the program measuring it never adds to a timing.

Many rows, one number

Now there are 223 ratios, one per row, and they need a summary. Which average you pick is itself a claim.

Predict: succinctly is 2x faster than jq on one row and 2x slower on another. What is its average speedup over the two? A guess is enough; decide before you open this.

1.00x: no speedup. A 2x win and a 2x loss cancel, and the geometric mean says so: √(2 × 0.5) = 1.00.

The ordinary mean of the ratios says (2 + 0.5) ÷ 2 = 1.25x, so if you guessed 1.25x, that is the misconception the geometric mean exists to fix. Turn the ratios round and work out jq's speedup over succinctly instead: the ordinary mean is again (0.5 + 2) ÷ 2 = 1.25x. Each tool would be "25% faster" than the other. The ordinary mean of ratios rewards whichever tool you put on top of the fraction. The geometric mean treats a factor of 2 the same in both directions.

On the 7950X's 223 rows the gap is large. The ordinary mean of the ratios is 4.58x, and the geometric mean, the figure every report quotes, is 3.18x. The difference is mostly a tail of a few huge wins: strings_upcase is 44-55x faster on the 7950X at every size. The reports quote the smaller number, and these tail rows are never the headline.

Read each line from left to right: on every chip the ratio grows with input size, from start-up to 100 MB. A constant-factor trick can't produce that curve. Doing less work per byte can, and that is the explainer's subject.

Then read the "jq faster on" column. On the M4 Pro, jq wins 26 rows, and start-up time decides every one of them. Twenty-one are small corpus files, two are the start-up rows, and three are ndjson_inputs_first, which reads only the first record of its input, even a 100 MB one. The slowest are args_many and ndjson_inputs_first at 0.68x. On the Graviton4, jq wins 7 rows, all between 0.96x and 0.99x. On the 7950X it wins none. jq also starts faster on Apple silicon: 0.69x on the M4 Pro.

Memory gets the same treatment, as a geometric mean of peak-memory ratios. At 100 MB succinctly holds less than half of jq's peak memory on all three chips: 0.41 of it on the 7950X, 0.48 on the Graviton4 and 0.46 on the M4 Pro. At 1 MB it holds more than jq: 1.06, 1.66 and 1.58 times as much.

How big is nothing? The A/A′ control

Every number so far is a ratio of two noisy measurements. Before you read meaning into a change in one, you need to know what no change looks like.

The tempting check is to compare today's run with yesterday's. But two runs hours apart differ in many things you did not change: the room temperature, what else woke up on the machine, how the OS laid out memory. A difference between two runs is a question, not an answer.

The control is an A/A′ comparison: time a binary against a byte-identical copy of itself, interleaved, exactly as you will time the real change. Whatever it reports is noise by construction, and that is the bar a real difference has to clear. The harness's --control flag does this for the jq comparison: it runs jq in succinctly's place, so the report shows jq against itself. For comparing two succinctly builds, the repository's scripts/ab-cli.py --control does the same with the older binary.

Ducky asks

If A and A′ are the same file, why would they ever differ?

In principle, they shouldn't. Whatever they do differ by is the resolution of your measurement, on this machine, today. A change smaller than that is not a finding, however many decimal places it has.

Same instructions, different speed

An A/A′ control bounds the noise of the machine. It can't bound the noise of building a different binary, because A and A′ share one code layout by construction.

Change any code, even code the benchmark never runs, and the linker may place the hot functions a few bytes away from where they were. On x86_64 that can change how the CPU's front end copes with a tight loop's branches, while it runs exactly the same instructions. In #3100, a change to math builtins, code the query never runs, made keys_unsorted on a 10 MB document 12% slower by minimum and 18% by median on the 7950X. The instruction counts were identical. To test it, the base was rebuilt with an inert padding function, which executes nothing and only shifts the code after it. Shifted by 112 bytes, the same query read 14.7% slower by minimum. Shifted by 128 bytes, it was back within 0.4%. The effect repeats every 64 bytes.

The repository's rule since then: on x86_64, a wall-clock difference between two builds whose per-function instruction counts agree is code placement, until a padding test says otherwise.

That makes the instruction count the second signal. Cachegrind counts the instructions a program executes, and neither machine load nor code placement moves that count. The harness adds it with --cachegrind on Linux, for rows up to 1 MB, since cachegrind runs about 50 times slower. A count can't see what the CPU does with the instructions, so it can't tell you how fast a build is. What it can tell you is whether the work changed. Time that moved while the count stayed flat came from the machine or the layout, not the code.

Release day: three rows 5-8% slower

Here is a measurement that needed all of this, from the day the 0.8.0 numbers were taken.

On the 7950X, the release commit's run took about two and a half hours. It was compared with a run of the previous commit from that morning. Three rows had become 5-8% slower relative to jq, by median and by minimum alike, while jq's own times on those rows barely moved:

Ducky asks

Three rows, all slower, minimum and median both past 5%, and jq flat. Isn't that a regression?

That is the question to answer before tagging the release. The check was the one from the A/A′ section: three binaries, timed interleaved on just these three rows. A was the previous commit, rebuilt. A′ was a byte-identical copy of A. B was byte-identical (same SHA-256) to the binary the release run had timed. Before any timing, each one's output on each row was checked against jq's.

Predict: timed side by side like this, how much slower is B than A on these three rows? About 7%, a few percent, or under 1%? Decide before you open this.

Under 1%: +0.1%, +0.1% and +1.0% by median, while A′ read within 0.1% of A.

The interleaved run had three rounds. In each round every binary ran 601 times on each 1 MB row and 301 times on the 10 MB row, taking turns, with an idle check before and after the round (no busy cores, load average 0.18-0.44). All of it took about a minute and a quarter.

The minimums are noisier than the medians here: between the identical copies, one round's minimum moved by up to 1.5%, so B's minimums are inside that range too. The instruction counts settle the rest. B executed 83, 99 and 77 fewer instructions than A, out of 13.8 million, 80.3 million and 17.8 million. The few that differ are in the same five libc and dynamic-loader functions on all three rows, by almost the same amounts whatever the input, so they belong to start-up, not to reading JSON.

Verdict: the slowdown belonged to the gap between two separate two-and-a-half-hour runs, not to the binary. We never found out what moved between those runs. The method doesn't need to know: taking turns put both binaries under whatever it was, and the difference went away. One row stays above the floor. users_length reads +1.0%, and every round agrees, so it is probably a real difference between the two builds. At an instruction count 77 lower, though, that is the size of change code placement makes on its own, and a fifth of what the long runs showed.

Why each guess was reasonable:

  • About 7% trusts the evidence as it looked: three rows, one direction, minimum and median agreeing. But that agreement is necessary, never sufficient, and the two runs had never shared a machine state.
  • A few percent splits the difference. Without a control, nothing can confirm or refute it. The A/A′ floor is what tells you what "a few" would have meant.
  • Under 1% is the right instinct when the diff can't reach the code being timed. But instinct is not evidence, and the minute and a quarter of interleaved timing is.

The committed 7950X report is that release run, these three rows included. Re-running until a row looks better would be cherry-picking of its own.

Check it yourself

The reports are committed. A claim you can rerun is worth more than one you have to trust.

Each chip's report is a pair of files in docs/compare/. The Markdown is for reading. The JSON has every row's samples, minimum, median, spread and peak memory, plus the run's env.json provenance: the commit, CPU, OS, toolchain, build features, and whether the timed binary was the stripped harness build. The commit measured was 955a984a3, and the 0.8.0 binary has not changed since. --verify reruns the deterministic parts against a committed report and spot-checks five of its timing rows, and exits 1 on any difference.

git clone https://github.com/rust-works/succinctly.git && cd succinctly
git checkout --detach 955a984a3

scripts/compare-jq-build.sh 1.7.1     # sha256-verified source builds into target/compare/
scripts/compare-jq-build.sh 1.8.2
scripts/sync-bench-corpus.sh          # the corpus files too large to commit

cargo build --release --locked --features cli,simd,regex,serde,bench-runner
./target/release/succinctly dev compare jq --full --huge

# or: rerun the deterministic parts and spot-check a committed report
./target/release/succinctly dev compare jq --verify docs/compare/jq-linux-x86_64.json

The 7950X run took about two and a half hours. On a Graviton4, --full takes about three hours and --huge adds about one. The 1 GB tier needs about 16 GiB of memory, because jq holds a 1 GB document at 9-11 GB. Check that the machine is idle before you start: the harness records the load, but it can't make the machine quiet.

mkdir -p ~/.config/succinctly
cp scripts/compare-ec2/compare-ec2.env.example ~/.config/succinctly/compare-ec2.env
$EDITOR ~/.config/succinctly/compare-ec2.env     # your region and bucket name

scripts/compare-ec2/compare-ec2.sh setup         # bucket, role, a security group with no inbound rules
scripts/compare-ec2/compare-ec2.sh bake          # an image with Rust and both pinned jq builds
scripts/compare-ec2/compare-ec2.sh run --commit 955a984a3

scripts/compare-ec2/ reproduces the Graviton4 report on a fresh instance (by default a c8g.2xlarge). The instance clones the commit, checks that HEAD is exactly it, builds, runs --full --huge, uploads the results and provenance to S3, and terminates itself. It has a hard time cap and an idle watchdog in case anything hangs. The repository's guide put a run at a few dollars in November 2026.

A reproduction fixes the commit, the jq sources, the inputs and the build's features, and checks each one. It does not fix the Rust toolchain, the OS image or the physical machine behind an instance type. It records those instead. So expect your numbers to agree with the committed ones to within the run's own noise, not to the last digit, and only on the same kind of chip.

What to ask of the next faster-than-jq claim

Before you open the list below, try to name the four checks from memory, each with the way of going wrong it guards against.

Compare with your list
  1. Did both tools do the same job? Output and exit status compared before any timing, on every row.
  2. Did they run under the same conditions? Interleaved within each repetition, never all of one and then all of the other.
  3. Is the average honest? Many rows, a geometric mean, a curve over input sizes rather than one ratio, and the rows the other tool wins listed by name.
  4. Is the difference bigger than nothing? An A/A′ control for the noise floor, and instruction counts to tell a change in the work from a change in the machine or the layout.

Then one more question, for any number at all: which chip? A figure without one can't be checked, and the next chip can tell a different story.

The trigger for the A/A′ habit is any comparison of two runs that weren't interleaved. A short experiment shows your own floor. Copy a binary (cp "$(command -v jq)" ./jq-copy) and time the original against the copy, taking turns, on a 1 MB input. Whatever difference it reports is the smallest one your setup can see.
