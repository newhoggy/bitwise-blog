Design document

What each visibility level hides, and from whom

The site's four visibility levels and its private-corpus guard, set against four adversaries: what each hides, what leaks by design, and the check behind every guarantee.

  • Answer: each level hides a page from some people, never from everyone. Unlisted only keeps the site from pointing a visitor or a crawler at a page, so anyone who looks can still list it; sealing stops everyone without the key; nothing stops someone with the repo from learning that a page exists, how big it is and when it changed.
  • Why it matters: a new feature is safe when it hands none of the four adversaries (visitor, crawler, repo reader, key holder) anything their level was meant to withhold. Every guarantee below names the check or test that holds it, and the ones nothing holds are listed.
  • Common mistake: treating "unlisted" as private, or a new key as revoking a leaked one. The old key still opens every version committed under it.

Hidden from whom?

Suppose someone adds a "Related posts" box to the foot of every post: the three pages that share the most tags with it. The obvious rule is to build it from every page in docs/ and leave out the ones marked hidden. That rule has no answer yet, because "hidden" means four different things here.

Built at index time, the box would write an unlisted page's title into the HTML of a listed one, which every visitor loads. It would link a post to an example page, which returns 404 on the published site. On the author's machine it could do worse: a private page's plaintext sits in docs/ beside the public pages, so the box could copy a private title into a public one. In CI, where only the sealed copy exists, the same code would find no tags for that page at all. Each of those is a different failure, against a different person. So the question a feature has to answer is not "is this page hidden?" but "hidden from whom, and does this feature hand that person something new?"

That needs a fixed list of who is looking. The rest of this page is that list, what each level withholds from each of them, and the code that keeps it so.

Four people who might look

Each has everything the one before has, and more: the last is a repo reader who also holds a key.

Casual visitor
Uses the published site in a browser: follows links, uses search, edits the address, reads the page source and the files the page loads. Does not dig through the repository.
Crawler
Fetches addresses it finds in links and in sitemap.xml, and honours robots.txt and the robots meta tag. Chat apps' link-preview bots count here: they read a page's head to draw a card.
Repo reader
Clones the public repository with its whole history: every source page, every generated file, every commit. The strongest adversary who holds no key.
Key holder
Has everything a repo reader has, plus one #k= link to a sealed page, whether it was shared with them on purpose or leaked.

The author's own machine, the 1Password account and anyone who can push to main are trusted, not adversaries. Out of scope says what that excludes.

What each level hides from whom

Here are the four levels against the four people. Each cell says, in words, what that person gets.

Two cells carry most of the misunderstandings. An unlisted page is readable by anyone with its address; the level only keeps the site from pointing at it. And a key holder reads more than the current page, for a reason What a key opens explains.

Normal and example pages

A normal page hides nothing from anyone: it is in the catalogue, search, the feed and the sitemap, and it has a social card. It is here as the baseline the other rows are measured against.

An example page only demonstrates the theme, so it is hidden from readers of the published site, and not from the repo: its source and its entries in the committed site data are public.

Unlisted pages: discoverability, not access

An unlisted page is published at its normal address and is fully readable there. What the level withholds is the site's help in finding it: no card, no search result, no backlink, no live link from a listed page, and a polite request to crawlers.

Can a casual visitor, who never opens the repo, list the title of every unlisted page? Answer yes or no before you open this.

Yes. Opening any page with #unlisted=true turns the flag on, and the home page then shows a card for every unlisted page. The flag is not a secret: it is written in this page and in the theme. Fetching theme/unlisted-pages.js directly gives the same list. "No" is the natural guess because the default page load really does carry no unlisted title, but that default protects against stumbling on a page, not against looking for one. Use a sealed page when the content must stay secret.

Sealed pages: content, not existence

A private page is written as a git-ignored docs/<slug>.private.html. npm run seal gzips it and encrypts it with AES-256-GCM under a random 256-bit key, and commits only the result, docs/<slug>.html: a fixed shell around the ciphertext. The key travels in the link's fragment, which browsers never send to a server. So the shell withholds the page's content and its card from everyone without the key, and it cannot withhold the file itself.

What a key opens

A key's reach is wider than one page in two directions. Across pages: several private pages can share a group key, and anyone with it opens every page in the group and sees every card in it on the home page. Back in time: the key stays the same across re-seals, so that old links keep working, which means it also decrypts every version of the page that was ever committed under it.

A key leaks. The author changes the page's group, so seal re-encrypts it under a new key and the old link stops opening the page on the site. What can the key holder still read: nothing, the old version only, or every version up to the change?

Every version up to the change. Re-keying protects the commits that come after it. Every earlier commit still holds a ciphertext the old key opens, and the repo is public with its history, so the key holder needs only git log and the old key. "Nothing" assumes the site is the only copy; "the old version only" forgets that every edit was sealed again under the same key. The only remedy is rewriting history, and a clone made before that keeps it anyway. Treat a leaked key as a permanent disclosure of everything it ever encrypted.

The key holder never gets other groups' pages or cards: each page's payload is encrypted under its own key, or its group's, and a card blob opens only under that key and that slug.

The private corpus

One more thing must never become public, and it is not a page: the writers' posts and everything derived from them, kept under the git-ignored corpus/private. The adversary is the repo reader, and the mechanism is that nothing derived from that text is committed.

The last row holds only on a clone that ran npm run hooks and has the private data linked. It fails open: without the hook setting nothing runs at all, and with the hook but no linked data it prints that nothing was checked and lets the push through, so an unlinked checkout skips the check on every push without failing. git push --no-verify skips it too, and so does a merge made on GitHub. CI cannot run it, because comparing needs the private text, and committing anything derived from that text (even hashes of its 8-word runs, which are guessable) is what the rule forbids.

What leaks by design

These are known and accepted. A feature that makes one of them worse needs a reason; one that adds a new kind needs a line here.

  • Every slug. Sealed pages' filenames, and their slugs again in theme/private-cards.js. Unlisted pages' paths in theme/unlisted-slugs.js, which any listed page may load, and in the GoatCounter dashboard, which counts unlisted pages like any other.
  • Sizes. A sealed payload is the page after gzip, plus 28 bytes of IV and tag, written in base64 (four thirds of that); a card blob is the same for its card.
  • Edit times and count. How many pages are sealed, and from the history, when each was re-sealed: the ciphertext and digest change only when the plaintext or the key does.
  • All of an unlisted page, to anyone who opens a page with #unlisted=true or fetches theme/unlisted-pages.js. Its title is also drawn on its social card, docs/assets/og/<slug>.png, which is published like any other.
  • All of an example page, to a repo reader.
  • A group key's reach: every page and card in the group, and a key's reach into history: every version it encrypted.
  • What GoatCounter receives for each public page view: the path, the title, the referrer, the screen size and the user agent.

Which pages share a group is not written in clear anywhere, but pages re-sealed in the same commit hint at it.

Out of scope

Defended

  • The four adversaries above, using the published site and the public repo.
  • Mistakes by the author that a check can see before a commit or deploy.

Not defended

  • A compromised browser or device, the author's or a reader's: the tab keeps keys in sessionStorage, and browser history may keep a full #k= address.
  • The 1Password account and its desktop integration.
  • Anyone who can push to main or change the workflows: they can change any mechanism.
  • GitHub and GitHub Pages as hosts, and GoatCounter's own script, which is not pinned and which this site trusts to drop the fragment.
  • Where a #k= link goes once shared: chat logs, mail archives, preview services.

Guarantees no check enforces

Each of these is a promise the code keeps today but nothing would catch it breaking. They are candidates for a check or a test, not known bugs.

  1. The plaintext of a private page is never committed. Only .gitignore stops it: a git add -f goes through, the pre-push hook looks only for corpus text, and the deploy job's refusal comes after the push. Unlike corpus/private, no test pins the ignore rule either.
  2. No #k= key is ever in a tracked file or a commit message. Nothing searches for one.
  3. No corpus text is pushed. The pre-push hook is the only check, and it passes open: a clone without core.hooksPath set pushes unchecked and says nothing, and one without the private data linked pushes unchecked after a single line saying so. Nothing fails when the check did not run.
  4. With the flag off, no unlisted title reaches the browser. The generated files are tested; that bh.js never requests theme/unlisted-pages.js is not.
  5. Links to an unlisted page are inert in the browser. check warns at the source; the rewriting in hideUnlistedLinks is untested.
  6. The sealed shell takes the key out of the address bar. The browser test opens a sealed page but never looks at the address bar afterwards. The exact shell comparison does not help: remove the history.replaceState call and every shell merely reads as outdated, which npm run seal -- --reshell clears.

Several rules that check does enforce have no test that fails when the rule is removed: the generic-shell comparison and the title and description searches, "sealed page must be noindex", a public page linking to a private one, a review of a private page, an orphan card, a public page sharing a slug with a private source, seal refusing to overwrite a public page, and the absence of private pages from theme/site.js and theme/search-index.js.

Judging a new feature

Back to the "Related posts" box. Run it through the four people:

  1. List what it adds, file by file: new markup in a page, a new field in a generated file, a new request, a new outside service.
  2. For each addition, ask each adversary what it now gives them that their level was meant to withhold. The box written into every post at index time gives a casual visitor unlisted titles; built in the browser from theme/site.js, it gives them nothing new, because that file has none.
  3. Check the levels it reads from. It must take its pages from the same lists as the catalogue (listedDocFiles, without examples) and never from a private source.
  4. Name the check that will hold it, add a row to the right table above, and if nothing holds it, add it to the list above.

The trigger for reaching for this page is any change that writes a page's title, path or text somewhere new: a generated file, a page's head, a request, a third party. That is where every leak listed here started.
