How succinctly reads JSON without building a tree

jq turns the whole document into a tree of values before your filter runs. succinctly jq turns it into two strings of bits instead, and answers the filter by counting bits in them. This page builds those bits for a 23-byte document, walks .a[1] through them by hand, and then says what they cost and what they don't check.

  • succinctly reads a JSON document once into a semi-index: one bit per byte that marks where each value starts, and two bits per value that record how the values nest. It finds any value by counting bits in those two strings, and decodes only the values a filter reads.
  • On a 1 GB file, that is the difference between holding about 1.24 times the file in memory and jq 1.7.1's 8.6 to 9.8 times, on each of the three chips the release was measured on.
  • The common mistake is to think a reader that skips the tree checks nothing. It checks every value it reads, with jq's own error message; what it skips is the values it never reads, unless you ask for --validate.

This page assumes you use jq and know what a bit and a byte are; it assumes nothing about succinct data structures. It is one of three pages behind the succinctly 0.8.0 announcement. If you already know rank, select and balanced parentheses, skip to what the index costs.

What jq does before your filter runs

Ask jq for one field of a big file and it still reads the whole file into a tree first: every object, array, string and number becomes a value in memory before the filter looks at any of them.

That is a fine design for a 10 KB document and an expensive one for a 1 GB document. succinctly's release comparison runs first(.users[])|.id over a 1 GB file of user records, a query that wants one number near the start. jq 1.7.1's peak memory on it is 8.57 times the file's size on an AMD Ryzen 9 7950X and on an AWS Graviton4 (ARM Neoverse-V2), and 8.86 times on an Apple M4 Pro.From the 1 GB tier of the committed reports, docs/compare/jq-*.md, run at commit 955a984. The file is 1,047.1 MiB. Almost all of that is the tree, and almost all of the tree is values the query never reads.

Here is the document this page uses, 23 bytes long, and the query we will answer from it:

$ cat doc.json
{"a": [1, "]"], "b": 2}
$ sjq -c '.a[1]' doc.json
"]"

Ducky asks

Why build anything? Search the text for "a", then read what comes after it.

Try it. The search finds "a" at byte 1, and the [ at byte 6 starts the array. To reach element 1 you must find where element 0 ends, so you scan forward for a comma or the closing bracket. Count brackets from the [, and the first ] you meet is at byte 11. That one is inside the string "]". A text search can't tell, so it decides the array ended after one element, and answers wrong. A search for "a" has the same problem with a string value that happens to be "a", or a key a one level down. And each new query would scan the text again.

So the text alone is not enough, and a tree is too much. What we need is a record, made once, of where every value starts and which values are inside which, that keeps none of the values themselves. That record is called a semi-index: an index of the document's structure, with the values left in the text until someone asks for one.The term and the design come from Ottaviano and Grossi's 2011 paper, linked under further reading. succinctly's JSON cursor is modelled on hw-json, a Haskell library.

Two strings of bits

succinctly scans the document once, byte by byte, and writes two strings of bits. The first says where values start; the second says how they nest.

The interest bits have one bit for every byte of the text. A byte gets a 1 when a value starts there: a { or [, the opening quote of a string, or the first character of a number, true, false or null. Every other byte gets a 0: closing brackets, commas, colons, spaces, and everything inside a string. To know that a byte is inside a string, the scanner carries a state from byte to byte: between values, in a string, just after a backslash in a string, or in a number or word. That state is how the ] at byte 11 gets a 0 where the text search went wrong.

The balanced parentheses have two bits for every value. Each 1 in the interest bits writes an open parenthesis, a 1 bit. A string or a number closes straight away, with a 0 bit, because nothing can be inside it; an array or object closes at its own closing bracket. Matching parentheses therefore enclose a value and everything inside it, and our document's seven values become (()(()())()()), the 14 bits 11011010010100.

Step through the figure. The first four steps build the index; the last five answer .a[1] from it. Watch the lines between the two strings: they turn a position in one into a position in the other.

The text, 23 bytes. succinctly keeps it as it is. Nothing below copies a value out of it; a value is decoded from these bytes only when the query reaches it.

Interest bits, one per byte. A 1 marks each byte where a value starts: { at 0, "a" at 1, [ at 6, 1 at 7, "]" at 10, "b" at 16 and 2 at 21. The ] at byte 11 gets a 0, because the scanner is in its in-a-string state there.

Balanced parentheses, two bits per value. Each value opens with a 1. The key "a", the numbers and the strings close at once with a 0; the array closes at index 8, where its ] is, and the object at index 13.

The two strings are in step. The k-th open parenthesis belongs to the k-th 1 in the interest bits, because the scanner wrote both at the same byte. Neither string stores the lines; they follow from the order, and counting recovers them, as step 9 shows.

.a starts at the root, index 0. It is the first open, so its byte is the first 1: byte 0, {, an object. Bit 1 is another open, so index 1 is the object's first child: the second open, the second 1, byte 1, the key "a". It matches.

The key's value is its next sibling. The key opens at 1 and closes at 2, so the next value opens at 3. No text was read to find it.

Every key is checked. jq keeps the last of two equal keys, so the lookup can't stop at the first match. The open at 3 is matched by the close at 8, which jumps over the whole array without reading a byte of it, and index 9 is the next key, "b" at byte 16. It doesn't match, so "a"'s value at index 3 stands.

[1]. Index 3 is the third open, so byte 6, [: an array. Its first element opens at 4 and closes at 5, so element 1 opens at 6.

Which byte is index 6? Count the opens before it: 4, at 0, 1, 3 and 4. So it is the fifth value, and its byte is the fifth 1 in the interest bits: byte 10. Counting the 1s before a position is called rank, and finding the fifth 1 is called select. succinctly decodes the string that starts at byte 10 and prints "]".

The figure's bits are not worked out by hand: a small program built against the succinctly 0.8.0 library printed them three ways, from the SIMD scanner the index uses on an ARM machine, the table-driven scanner and the plain byte-at-a-time state machine, and all three agree. It also ran the walk above through the library's cursor and got the same indexes and byte 10.

Counting is the navigation

Every move in the walk was one of three operations on the parentheses, and the one jump from the parentheses back to the text was rank followed by select.

This is how succinctly's cursor turns a position in the parentheses into a byte of the text. A cursor is nothing but that position:

pub struct JsonCursor<'a, W> {
    text: &'a [u8],
    index: &'a JsonIndex<W>,
    bp_pos: usize, // a position in the parentheses
}

pub fn text_position(&self) -> Option<usize> {
    let rank = self.index.bp().rank1(self.bp_pos); // opens before this one
    self.index.ib_select1_sequential(rank)         // the byte of that interest bit
}

The moves through the tree are just as small. A value's first child is the next bit, if that bit is an open; its next sibling is one past its matching close, if that is an open. Step 6 was one of each.

pub fn first_child(&self, p: usize) -> Option<usize> {
    if self.is_open(p) && self.is_open(p + 1) { Some(p + 1) } else { None }
}

pub fn next_sibling(&self, p: usize) -> Option<usize> {
    let close = self.find_close(p)?;
    if self.is_open(close + 1) { Some(close + 1) } else { None }
}

Ducky asks

Haven't we just moved the problem? Counting the opens before position 6 is easy. Counting the opens before position 60 million is a scan of 60 million bits.

It would be, with nothing else stored. So succinctly stores a little more: small directories of counts, built in the same pass, that turn each count into a lookup.

  • Rank keeps a running total of 1s at the start of every 64-bit word. The 1s before position p are the total stored for p's word, plus a popcount (one CPU instruction) of that word's bits below p. For the interest bits the totals are 32-bit numbers, one per 64 bits; the parentheses use a two-level version of the same table.
  • Select looks for the word whose running total passes k, by binary search over the same totals, then finds the bit inside that one word. A walk in document order, like printing a whole document, starts each search where the last one landed, so it takes a few probes, not a full binary search.
  • Matching a parenthesis is quick for a string or number, which is most of a document's values: its close is the very next bit. For an array or object, the parentheses keep the lowest nesting depth reached in each word, each 32 words and each 1,024 words, so the search can skip any block that cannot hold the match. That is how step 7 jumped the array.

Everything from here down changes how fast the index is built and walked, not what it holds. The real scanner doesn't loop over bytes one at a time: it uses lookup tables, and SIMD on x86-64 and ARM, and a differential test runs every scanner a target compiles over every short combination of the bytes that matter, over random bytes and over mangled documents, and requires the same bits as the byte-at-a-time rules.The rules are state_machine in src/json/standard.rs; the test is tests/json_builder_differential_properties.rs. The cursor operations shown here are the library's public API, and the jq evaluator adds many shortcuts on top of them that this page doesn't cover.

What the index costs

The index is far smaller than a tree, but it is not free, and its size depends on how densely the document packs its values.

succinctly's users test file has a value every 7.8 bytes on average. Estimate the index's size as a share of the file: about 5%, about 25%, or about 100%? Commit to one before you open this.

About 25%: it measures 23.8%. Add up the parts you have already met. The interest bits are one bit per byte, 1/8 of the file: 12.5%. Their running totals are 32 bits per 64, half as much again: 6.25%. The parentheses are 2 bits per value, and a value every 7.8 bytes makes that 2 ÷ (8 × 7.8) = 3.2%. Their directories add 1.9%, and 12.5 + 6.25 + 3.2 + 1.9 is about 23.8%.

If you said 5%, you counted the parentheses and their directories and forgot that the interest bits cost a bit for every byte, value or not. If you said 100%, you were thinking of a copy of the document, which the index never makes; a tree costs several times more than that.

The interest bits and their totals cost the same 18.75% on every document. The parentheses add more where the values are packed tighter. Here is the same sum for four of succinctly's generated test files, measured by building the index with the 0.8.0 library and adding up its bit strings and directories:

On the 1 GB file of user records, succinctly's peak memory is 1.24 times the file on the 7950X and on Graviton4, and 1.25 times on the M4 Pro: the file's own bytes, plus an index of about a quarter of them. jq 1.7.1 on the same file holds 9.48 times the file to print it with . on the 7950X and Graviton4, and 9.77 times on the M4 Pro.These are peak resident memory from the 1 GB tier of the reports, of the comparison harness's own build of succinctly (features cli,simd,regex,serde plus bench-runner); the release archives are built with cli alone.

Ducky asks

A quarter of the file is a lot for an index. Why spend a bit on every byte? Why not keep a list of the bytes where values start?

Because the list costs more on this file. Each entry would be a 4-byte offset, 32 bits per value. The interest bits and their totals cost 1.5 bits per byte, which at a value every 7.8 bytes is 11.7 bits per value. The list would only be smaller when values are more than about 21 bytes apart, as in the strings file.

The other cost is time up front. The index covers the whole document and is built before the filter runs, so first(.users[])|.id holds the same 1.24 times the file as . does. The saving is in what happens next: no value is built until the filter reads it.

What it does not check

jq refuses a malformed document before the filter runs. succinctly checks each value as the filter reads it, so a fault in a part the filter never reads goes unnoticed.

Do {"z":1 "y":2}, which is missing its comma, and {"z":1,"y":2} get the same index, or different ones? Decide before you open this.

The same. Both get the interest bits 1100010100010 and the parentheses 1101010100. A comma or a colon writes nothing to either string, so the index can't hold its absence. In the same way tru indexes exactly as 1 does: both are a byte where a value starts.

If you said different, you were picturing an index that records the commas. That would cost a bit for each one and would still not be a validator: it could not tell tru from true.

So a fault in the index's blind spots is found when the faulty value is read, and not before. Break element 0 of our document and ask for element 1:

$ cat broken.json
{"a": [tru, "]"], "b": 2}
$ sjq -c '.a[1]' broken.json
"]"
$ sjq -c '.a[0]' broken.json
jq: parse error: Invalid literal at line 1, column 11
$ jq -c '.a[1]' broken.json
jq: parse error: Invalid literal at line 1, column 11
$ sjq --validate -c '.a[1]' broken.json
jq: validation error: invalid keyword 'tru' (expected null, true, or false)
  --> broken.json:1:8
     |
   1 | {"a": [tru, "]"], "b": 2}
     |        ^

The read of element 0 fails with jq's own message and exit status 5. The read of element 1 never touches tru, and succeeds where jq 1.7.1 refuses the file. --validate runs a strict RFC 8259 check of the whole document before the filter, and exits with status 3.

Why not always validate? Because a full check reads every byte, which is the work the index exists to skip. One indicative measurement in succinctly's architecture notes put strict validation of an 8.4 MB file at 8.6 ms: two thirds as much again as a query like .users[0].name, and under 5% of printing the whole file with ..On an Apple M5 Max, minimum of 7 runs with process start-up subtracted, not interleaved and not on an idle machine; the notes ask for a re-measure before relying on the exact figures. Invalid UTF-8 is the exception: checking it is cheap, so it is done for every document as it is read.

This is one of succinctly's recorded differences from jq, the kind it permits only where matching jq would cost what the design is for. The rule, and the record of every difference, are on the compatibility page.

Rebuild it yourself

Without scrolling back up, write the interest bits and the parentheses for [1,[2]], then work out which byte element 1 starts at.

Show the answer

Interest bits 1101100, parentheses 11011000. The values start at bytes 0 ([), 1 (1), 3 ([) and 4 (2); the comma and the two closing brackets get 0s. The parentheses are open for the outer array, 10 for the 1, open for the inner array, 10 for the 2, then a close for each array.

Element 1 starts at byte 3. Element 0 is index 1, the first child of the root. It opens at 1 and closes at 2, so element 1 opens at index 3. Two opens come before index 3, so its byte is the third 1 in the interest bits: byte 3, the inner [. succinctly agrees:

$ sjq -c '.[1]' small.json
[2]

Reach for this kind of index when the document is large and a query reads a small part of it, or when the memory a tree would take is the problem. A tree still wins when the document is tiny and the run is mostly process start-up: on an Apple M4 Pro jq 1.7.1 starts faster, as the announcement's Where jq still wins section shows.
