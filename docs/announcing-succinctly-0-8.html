succinctly 0.8: a jq you can trust, three times faster

Plenty of tools are faster than jq. The hard part is being faster while giving the same answers, down to jq's own quirks, and proving both in public. succinctly 0.8.0 is a drop-in replacement for jq 1.7.1: about three times faster across 223 measured workloads on three chips, with every place it answers differently written down.

If you only want to try it, the next section takes 30 seconds. The four after it back one claim each: Fast, Faithful, Lean and Honest. Then comes the part a release post usually skips: where jq is still the better tool.

Try it in 30 seconds

Install the binary, create the short aliases, and run sjq wherever you would run jq.

  1. Install. cargo install succinctly --features cli, or unpack one of the release archives.The macOS archive needs macOS 12 or newer, the x86-64 archives a CPU with POPCNT (2008 or newer), and the Linux archives the glibc of Ubuntu 24.04 or newer. cargo install builds for your own machine and has none of these floors.
  2. Add the aliases. succinctly install-aliases puts sjq, syq, sjq-locate and syq-locate next to the binary.
  3. Compare. Run a filter you already use through both tools and diff the output.
$ succinctly --version
succinctly 0.8.0
$ cat users.json
{"users":[{"name":"Ada","langs":["ml","rust"]},{"name":"Grace","langs":["cobol"]}]}
$ P='[.users[] | {name, langs: (.langs | length)}]'
$ jq -c "$P" users.json
[{"name":"Ada","langs":2},{"name":"Grace","langs":1}]
$ sjq -c "$P" users.json
[{"name":"Ada","langs":2},{"name":"Grace","langs":1}]
$ diff <(jq "$P" users.json) <(sjq "$P" users.json) && echo identical
identical

The binary also answers to the name jq. A symlink called jq earlier on your PATH (ln -s "$(command -v succinctly)" ~/bin/jq) runs your existing scripts on it unchanged, and deleting the link puts them back on jq.

Why a faster jq matters

jq sits in the middle of shell scripts, CI jobs and log pipelines, and nobody notices it until a document gets large. Then it is the slow step, or the step that runs out of memory.

Here is one ordinary command, jq ., pretty-printing a 1 GB file of user records on an AMD Ryzen 9 7950X:

. over a 1 GB array of user records, median of 3 interleaved runs, AMD Ryzen 9 7950X.
ToolTimePeak memory
jq 1.7.125.9 s9.7 GiB
succinctly jq3.1 s1.27 GiB

jq builds the whole document as a tree of values before it runs the filter, and that tree takes almost ten bytes of memory for every byte of input. A faster jq is easy to want. The trouble is that a script written for jq depends on far more than the filter language: how numbers are printed, which error comes out and with what exit code, what happens on the edge cases nobody tested. A tool that is fast but answers a little differently moves the cost from your CPU to your debugging time.

So 0.8.0 was built around one question: can a jq be several times faster and still give the same answers, every time, provably? At 0.7.0, in April, succinctly was a succinct-data-structures library with a jq-flavoured command line. About 3,000 merged pull requests later, it is a jq 1.7.1 replacement whose differences are all listed and whose speed figures anyone can regenerate.

Fast: about three times jq, and more as inputs grow

Across all 223 workloads the geomean speedup is 3.18x on an AMD Ryzen 9 7950X, 3.10x on an AWS Graviton4 (ARM Neoverse-V2) and 2.84x on an Apple M4 Pro. The lead grows with the size of the input.

Each workload, which the reports call a row, is one jq program over one input: field access, select, map, group_by, regex, @csv, NDJSON streams, early exits, plain pretty-printing, over generated documents of several shapes at 1, 10 and 100 MB, plus small real files and process startup. The chart groups them by input size.

Why does the lead grow? A fixed cost, starting the process, is the same for both tools at any size, and at 1 MB it is still a good part of the run. What grows with the input is the cost of reading it, and that is where succinctly does less work. Instead of a tree of values it builds a compact structural index of the text, and it turns into values only the parts the program reads. How succinctly reads JSON without building a tree walks through that index.

Ducky asks

Three times faster. Isn't that just a Rust tool using all my cores?

Predict: how much of the 3x comes from running on more than one core? Most of it, some of it, or none? Commit to a guess before you open this.

None of it. succinctly jq runs one thread. The reports measure CPU time over wall-clock time for . on a 10 MB input, where a ratio near 1.00 means one thread: it is 0.50 on the 7950X and the M4 Pro and 1.00 on the Graviton4, against jq's 0.94 to 0.97. Neither tool uses more than one core.

"Most of it" is the natural guess, because many modern command-line tools win that way. "Some of it" is the guess that a little parallel parsing helps on big files. The real difference is the amount of work per byte, which is also why the gap widens with size rather than staying a constant multiple.

Faithful: jq's answers, including its quirks

The jq mode follows jq 1.7.1 bug for bug. It differs only for a stated reason, and every difference is recorded.

"Compatible" usually means "the common filters work". For a tool that replaces jq inside scripts, the bar has to be the output bytes and the exit status, on the odd inputs as well as the common ones. Three small cases, each captured from jq 1.7.1, jq 1.8.2 and the 0.8.0 binary:

The first row is jq's number handling: a literal is printed with the exact digits it was written with, 1E2 becomes 1E+2, and arithmetic falls back to a double. The second is a case where jq 1.8 changed the behaviour and succinctly keeps 1.7.1's, because 1.7.1 is the version it replaces.

Ducky asks

Why copy jq's bugs at all? Wouldn't fixing them be better?

Better for a new script, perhaps, but a script that already runs was written against the jq that has them, and a "fix" is a change in what that script prints. So the default is to match, and the exceptions are narrow: output jq could not read back, a result that would corrupt data or drop a write, a crash, or a bug that jq 1.8 has fixed itself. The third row is that last case: jq 1.7.1's last answers null for a generator that yields nothing, jq 1.8 fixed it, and succinctly follows the fix. Bug for bug: what jq compatibility means sets out the rule that decides each case.

What the comparison checks, identically on all three chips:

  • jq's own test suites: 446 of the 447 cases in jq 1.7.1's jq.test, all 224 in man.test, 39 of 40 in onig.test and 7 of 7 in base64.test. The two misses are the two places where succinctly follows a jq 1.8 fix: a NaN with a payload is an invalid number (CVE-2024-53427, #7522), and a regex group that takes no part in an empty match is unmatched (#7520).
  • Generated programs: 6,000 random programs and documents from a typed grammar, over three fixed seeds. jq itself fails to compile or times out on 104 of them. Of the other 5,896, all but 2 give jq's exit status, jq's output and jq's class of error, and the 2 are again jq 1.8 fixes.
  • Builtins and flags: 201 of 207 builtins agree on eight probe inputs each; the six that differ depend on the host (get_jq_origin, the libc's weekday in strptime), are a crash in jq (strftime on a non-string format), or follow 1.8. Of 490 command-line probes, 459 to 464 agree; the rest are by design, such as --version naming succinctly, or follow 1.8.

Each of those differences is an entry in a ledger, which holds 65 in all, and CI fails if the comparison finds a difference the ledger does not list, or an entry that no longer differs. At 0.8.0 both counts are 0. The full list is docs/compliance/jq/limitations.md.

Lean: less than half of jq's memory on large inputs

From 10 MB up, succinctly jq peaks at less memory than jq on every chip, and at 100 MB less than half. Below that it uses more, and the table says so.

The small-input column is a fixed cost: a run that reads no input peaks at about 4 to 7 MiB in succinctly against jq's 2.5 to 2.9 MiB, and at 1 MB that fixed part is still most of succinctly's peak. As the input grows, what counts is what each tool keeps per byte of input. jq keeps a tree of values. succinctly keeps the text itself plus an index of about a fifth to two-fifths of the input's size (what the index costs). The best rows, pretty-printing or compacting a 100 MB document, peak at 0.12 to 0.14 of jq's memory.

Predict: for . over the 1 GB document in the table above, jq peaks at 9.7 GiB. Roughly how much does succinctly need: about 5 GiB, about 1 GiB, or a few MiB?

About 1 GiB: 1.27 GiB, on all three chips. That is about 1.25 times the 1.02 GiB document (the text itself, plus its index and what printing needs), where jq's 9.7 GiB is about 9.5 times it.

"About 5 GiB" is what you get if you assume any jq must build some tree of the document, just a tighter one. "A few MiB" is the streaming intuition: true for a stream of many small values, where 0.8.0 reads a large NDJSON file a piece at a time, but one 1 GB array is one value, and . has to print all of it. The floor for a single document is having the text at hand, and the index is what keeps the rest small.

Honest: numbers you can regenerate

A speed claim is only as good as the method behind it. Every figure on this page comes from reports committed to the repository, and the tool that wrote them ships with the source.

  • Output first, timing second. A row's time counts only if both tools printed the same bytes. All 223 rows passed that gate on all three chips.
  • Interleaved repetitions. jq and succinctly alternate within each of 21 repetitions per row, so a machine that warms up or slows down during a run affects both alike. Running all of one tool and then all of the other once made an improved binary measure up to twice as slow.
  • Geomean, not the best row. The headline is the geometric mean over every row, which a few very fast rows cannot dominate. The reports also flag each row whose spread is above 5%, and list every row jq wins.
  • Each chip measured on its own. No figure is carried from one architecture to another. An earlier optimisation measured 6.1x on an M4 Pro and 16.4x on a Zen 4, which is why the reports cover three chips.
  • Reproducible end to end. scripts/compare-jq-build.sh builds the pinned jq releases from source, succinctly dev compare jq --full regenerates a report, and scripts/compare-ec2/ reruns the Graviton4 report on a fresh AWS instance. Reproducing the comparison has the steps.

The method earned its keep during the release itself. The release-commit run on the 7950X showed three rows 5% to 8% slower relative to jq than a run of the previous commit that same morning, and the only code change between the two never reached those rows. Re-timed interleaved, beside an A/A' control of two copies of the old binary, the two copies agreed within 0.1% and the new binary was within 0.1% to 1.0% of the old by median; instruction counts moved by fewer than 100 out of 13.8 to 80.3 million. The shift was between two separate runs of two and a half hours each, not in the binary. Benchmarking against jq honestly tells that story and the rest of the method.

The same discipline also measured the release getting faster. A run a week earlier, before the final round of fixes, read 2.74x on the 7950X, 2.71x on the Graviton4 and 2.56x on the M4 Pro, with jq faster on 9, 28 and 30 rows.

Where jq still wins

"About three times faster" is a geomean, and a geomean has rows below it. These are the cases where jq is the better choice today, or where succinctly behaves differently on purpose.

  • Startup on Apple silicon. With no input to speak of, jq starts faster on the M4 Pro (0.69x). That accounts for all 26 rows jq wins there: startup-bound programs such as args_many and ndjson_inputs_first (0.68x, which reads one value and stops), and small real files such as a 2.7 KB npm package.json. On Linux startup is a tie or better (1.01x on the Graviton4, 1.19x on the 7950X), and the Graviton4's 7 losing rows are all between 0.96x and 0.99x. If your workload is thousands of tiny documents on a Mac, keep jq.
  • Memory on small inputs. At 1 MB succinctly peaks at 1.06x to 1.66x of jq's memory, as the memory table shows.
  • Binary size. Stripped, the measured binary is 17 to 21 MiB against jq's 0.8 to 0.9 MiB, roughly twenty times larger.
  • Malformed input it never reads. jq parses the whole document before it runs, so any syntax error fails the run. succinctly reads lazily, so a filter that never reaches the bad token gets its answer. Ask for jq's strictness, and more, with --validate:
$ echo '{"a":1,"b":tru}' | jq -c .a
jq: parse error: Invalid literal at line 1, column 15
$ echo '{"a":1,"b":tru}' | sjq -c .a
1
$ echo '{"a":1,"b":tru}' | sjq --validate -c .a
jq: validation error: invalid keyword 'tru' (expected null, true, or false)
  --> <stdin>:1:12
     |
   1 | {"a":1,"b":tru}
     |            ^
  • A pipe that stays open. succinctly reads standard input to its end before the program runs, except under --stream. tail -f app.log | jq -c .msg prints as lines arrive; with sjq it prints nothing until the pipe closes. For live streams, use jq or --stream.
  • jq 1.8's new features. succinctly targets jq 1.7.1, so it agrees with 488 of the 550 cases in jq 1.8.2's jq.test. If you rely on 1.8, stay on 1.8.
  • A few recursive programs. Very deep recursion is refused at the native stack's limit where jq keeps going, and a handful of recursive shapes cost more time or memory than in jq. The answers are jq's wherever they finish; each case is an open issue on the limitations page.

The repository's guide to choosing between jq and succinctly jq ties each of these to the report rows behind it, and a test fails when a regenerated report stops supporting one.

Also in 0.8.0

  • jq's stream flags: --stream, --stream-errors and -b are supported, alongside --seq.
  • Streams in flat memory: a large NDJSON or --seq file, or a big pipe of them, is read a piece at a time, so a plain filter's peak memory stays at a few MiB however long the stream is.
  • Locale-aware dates: strftime and strflocaltime use the names and layouts of LC_TIME, as jq does.
  • succinctly yq, as a preview: it aims to follow yq v4.53.3, including many of yq's input and output formats (XML, TOML, CSV, TSV, properties, INI, KYAML). Its known differences are on the yq limitations page.
  • The comparison harness: succinctly dev compare jq, which produced every number above.
  • For library users: rust-version is 1.89.0, now checked in CI; the crate ships src/ only and is 6.9 MB; BitVec and BalancedParens gain select0.

The 0.8.0 section of the changelog runs to over 2,200 entries, most of them fixes that brought one more corner of jq's behaviour into line.

Get started

  1. Install with cargo install succinctly --features cli, or from the v0.8.0 release.
  2. Run succinctly install-aliases, then use sjq in place of jq, or link it in as jq.
  3. Check it on your own data: diff its output against jq's on the filters your scripts use. If they differ and the difference is not on the limitations page, that is a bug: open an issue.
